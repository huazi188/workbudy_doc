# 第一部分：国内 / China

### 1. 方案名：阿里开源 Open Code Review——确定性规则层+LLM 层的精确率优先 PR 评审 Agent 【研发代码评审·阿里巴巴·A类方案】

**① 场景与边界**
- 干什么：在 PR 合入前做行级代码评审——文件选择、diff 分组、已知漏洞模式匹配、跨文件上下文分析、生成带依据的行级评论。
- 输入：代码仓库的 PR diff（支持 GitHub Actions、GitLab CI，CLI 亦可指定 `--from main` 或 `--commit <sha>`）。
- 输出：行级评审评论（可导出 JSON 供 CI 消费），以及与 Claude Code 打通后的独立修复实现（`/review`）或委托评审（`/delegate-review`）。
- 不干什么：官方仓库明确它"是评审者不是 Agent"——不重构代码库、不写测试、不做架构决策、不做自主代码生成；且有意用召回率换精确率，不做穷举扫描。

**② 工具清单**

| 工具 | 作用 | 输入 | 输出 |
|---|---|---|---|
| 确定性层（规则匹配） | 匹配已知缺陷模式：空指针、线程安全违规、XSS、SQL 注入 | 文件列表+diff | 命中规则清单 |
| 确定性层（diff 分组） | 智能筛选评审文件、合并相关 diff，避免全量送审 | 仓库变更集 | 评审范围 |
| LLM 层 | 动态决策、跨文件上下文理解、生成行级评论 | 筛选后的 diff+规则命中结果 | 行级 comment |
| OCR CLI | 编排入口：`ocr review` / `ocr config provider` / `ocr config model` / `ocr session list` | 命令行参数 | 评审会话与结果 |
| CI 集成 | GitHub Actions / GitLab CI 开箱支持，结果导出 JSON | CI 事件 | 流水线评审报告 |
| Claude Code 插件 | `/review`（全流程+独立修复）、`/delegate-review`（OCR 定范围，Claude 出评审） | 仓库上下文 | 评审/修复结果 |

**③ 编排流程**
单 Agent 内嵌两段式管线（无多 Agent 编排）：

```text
PR 变更 → 确定性层（文件选择 + diff 分组 + 已知模式规则匹配）
        → LLM 层（动态判断 + 跨文件上下文 → 生成行级评论）
        → 结果导出 JSON / CI 评论
        → （可选）Claude Code 插件接管修复或委托评审
        → 会话可中断恢复（ocr session list）
```

**④ 关键配置**

```text
模型/Provider 可切换      # ocr config provider、ocr config model，官方支持多 Provider
评审范围=确定性层筛选结果  # 不做全仓评审，只送筛选后的 diff
召回策略=精确率优先        # 官方明确 trade recall for precision
timeout / max_retries     # 原方案未涉及
```

**⑤ 失败与兜底**
- 会话中断 → `ocr session list` 恢复续跑，不从头再来。
- 精确率与召回率冲突 → 官方明确牺牲召回保精确：宁可少报，不制造"狼来了"（行业基线是开发者把 56.3% 的 AI 评审意见判为误报）。
- LLM 层误报 → 确定性层先把已知模式拦掉，LLM 只处理边缘情况，降低误报面。原方案未涉及转人工机制。

**⑥ 验收指标**
| 指标 | 目标值 |
|---|---|
| 精确率/F1 | 高于通用 LLM Agent（在 50 个开源仓库、200 个真实 PR、10 种语言、1505 个标注问题上验证，80+ 名阿里资深工程师参与标注） |
| Token 成本 | 约为通用 Agent 方案的 1/9 至 1/15 |
| 误报率 | 显著低于行业基线 56.3% 被拒 |
| 项目热度 | GitHub 53,900 star（六个月） |

**机会点**：阿里的确定性规则层是现成的"评审规则资产"，中小团队真正缺的是自己的规则集——把它抽出来做成可订阅的行业缺陷规则包（金融版/电商版各 50 条），第一步 fork 仓库整理规则模板，两周即可在 10 个团队内测。

来源：[Alibaba Open Code Review 报道](https://wpnews.pro/news/alibaba-open-code-review-ai-code-reviews-at-1-9-the-cost)、npm 包 `@alibaba-group/open-code-review`（最近更新 2026-11-18）

### 2. 方案名：Ryt Bank 双守卫银行智能体——输入/输出护栏+KYA 智能体身份链 【金融 KYC/AML·Ryt Bank×蚂蚁数科·A类方案】

**① 场景与边界**
- 干什么：数字银行开户场景的 eKYC 拦截"骡子账户"（mule account）、AML 名单精细比对（自动检索公开网络信息、识别姓名变体并与马来西亚金融体系 AML 名单比对）、需要多轮权衡的准入判定。
- 输入：开户申请与客户身份材料、客户公开网络信息。
- 输出：准入/拒绝/补充材料后的再判定结论，全程带可追溯调用链。
- 不干什么：智能体执行的是用户意图，不拥有独立行动人格；需要授权时向用户请求授权，而不是自行决定。

**② 工具清单**

| 工具 | 作用 | 输入 | 输出 |
|---|---|---|---|
| 蚂蚁数科 eKYC 服务 | 开户身份核验（其同时服务马来西亚最大电子钱包之一 Touch 'n Go，具备大规模实践数据） | 客户身份材料 | 核验结果 |
| 公开网络检索+AML 名单比对 | 检索个人公开信息、姓名变体，比对 AML 名单 | 客户姓名/身份 | 比对结果与疑点 |
| 输入侧守卫智能体（Guardrail） | 判断请求是否属于金融业务：转账类放行，无关/危险请求直接拒绝 | 用户请求 | 放行/拦截 |
| 输出侧守卫智能体 | 拦截错误、拼凑、误导或危险信息的结果 | 模型输出 | 放行/拦截 |
| 加密安全凭证+调用链校验 | 每个智能体持有加密凭证访问核心银行系统；校验"用哪个基础模型、托管在哪、经过哪些调用" | 智能体调用请求 | 身份确认/拒绝 |

**③ 编排流程**
多智能体（守卫+业务智能体+人工环节）：

```text
用户请求 → 输入守卫（金融业务相关？否→拒绝）
        → 业务智能体执行（eKYC / AML 检索比对）
        → 多轮补充判定（可疑但补充收入流水后可准入的场景，多轮权衡而非一次判定）
        → 输出守卫（拦截错误/误导输出）
        → 人在环路（Human-in-the-Loop 为默认设计，非事后补丁）
        → 红队持续对抗测试 → 发现即修复
```

**④ 关键配置**

```text
max_steps / timeout / max_retries  # 原方案未涉及
模型选择                            # 原方案未涉及（仅明确模型本身纳入 KYA 身份校验维度）
温度                                # 原方案未涉及
```

**⑤ 失败与兜底**
- 越权/危险请求 → 输入守卫直接拒绝，不进入业务执行。
- 输出拼凑或误导 → 输出守卫拦截。
- 判定存疑 → 默认转人工（人在环路为默认设计）；多智能体分工处理"看似可疑但补充材料后可准入"的灰度案例。
- 智能体身份伪造 → 调用链全维度校验（模型、托管位置、调用历史）。

**⑥ 验收指标**

```text
原方案未涉及（文中未给出拦截率、误判率等量化指标）
```

**机会点**：KYA（识别智能体及其权限来源）是监管迟早会要求的空位——国内还没有给持牌机构用的"智能体调用链审计日志"标准件，第一步做一个把"哪个智能体、哪个模型、经过哪些调用"落成审计日志的 SDK，拿一家出海数字银行做 Demo，1-3 个月可验证。

来源：[腾讯新闻 KYA 研究（2026-11-18）](https://news.qq.com/rain/a/20261118A08OD500)

### 3. 方案名：保险四岗多智能体协同——客服/核保/培训/外呼共享同一知识底座 【保险核保协同·实在智能 Soiawork·A类方案】

**① 场景与边界**
- 干什么：保险机构四个岗位的智能体协同——客服条款速查与工单摘要、核保缺件预检与疑点汇总、培训案例卡与陪练、外呼名单筛选与合规管控。
- 输入：客户咨询（企微/电话）、核保材料（体检报告、财务问卷）、会话记录、监管新规与规则变更。
- 输出：带出处的客服答案、核保疑点清单（不出结论）、培训案例卡、外呼摘要与意向分级。
- 不干什么：判断决策类不碰——承保结论、理赔核定、销售适当性必须由持牌责任人出具，智能体只"把依据备齐、把疑点标出来"；核保不出加费/除外/拒保结论；规则未覆盖必须标注"无对应规则，需人工判断"。

**② 工具清单**

| 工具 | 作用 | 输入 | 输出 |
|---|---|---|---|
| 可版本化知识库 | 客服/核保/培训/外呼共用同一份条款、规则、话术，带生效时间与版本 | 文档+规则变更 | 带出处的检索结果 |
| 连接器 | 对接业务系统取工单与保单状态 | 业务系统接口 | 工单/保单数据 |
| 设备（Soia Worker） | 操作不开放接口的老系统（界面操作+数据读取），保留录屏与日志 | 受控环境指令 | 老系统数据 |
| 工作流 | 固定确定性步骤：取名单→校验规则→生成话术→执行→摘要回写→转人工 | 任务定义 | 流程执行记录 |
| 自动任务 | 按周/按月定时运行（培训素材收集、报表生成） | 定时配置 | 任务产出 |
| 运行记录 | 每次查询/预检/外呼留痕，可回答"依据哪一版规则" | 全部执行事件 | 可追溯日志 |

**③ 编排流程**
多智能体+工作流交接（四岗不互相"对话"，靠共同底座交接）：

```text
客户提问"既往症能否赔" → 客服智能体：意图识别 → 知识库调条款依据 → 回答能答部分
  → 需要核保口径 → 生成待核保任务（附告知信息与投保记录）
  → 核保智能体预检：列缺失材料、比对规则、标临界指标 → 疑点清单
  → 核保人确认出具意见 → 意见回写知识库（新增标准问答对）
  → 培训智能体转案例卡进下周陪练
  → 客户在续保节点 → 外呼智能体按规则加入回访（话术带本次结论）
  → 全程留痕
```

落地节奏（原文明确）：第一步选一个高频低风险场景试跑（条款速查或缺件预检）；第二步每周抽查输出，重点看依据引错、该转人工没转、该拦没拦三类问题；第三步再扩展，外呼放最后。

**④ 关键配置**

```text
max_steps / timeout / max_retries  # 原方案未涉及
模型选择 / 温度                     # 原方案未涉及
拨打时段、最短间隔、拒接冷却期       # 原方案要求写进自动任务，未给具体值
```

**⑤ 失败与兜底**
- 依据引错 → 每周抽查机制，作为重点检查项；知识库条目带生效时间与版本，过时口径可识别并下线。
- 该转人工没转 → 越界拦截规则："能不能赔""该不该买"类问题不直接回答，生成待办转核保/理赔岗并告知客户预计回复时间。
- 该拦没拦 → 外呼链路任何一步触发合规条件即停下等人工确认。
- 责任归属 → 结论由核保人出具，责任不因使用智能体转移。
- 死循环规避 → 原方案未涉及。

**⑥ 验收指标**

```text
原方案未涉及（仅有方法论级的"验证取数准不准"，无量化目标）
```

**机会点**：文章把边界和方法论写得很清楚，但核保"缺件预检"这个单点工具目前只有保险机构自己在内部摸索——用开源 RAG 给一家保险中介做缺件清单原型（输入保单类型，输出缺失材料清单），万元级成本、两周能见第一个正反馈。

来源：[实在智能：保险多智能体应用怎么做（2026-11-19）](https://www.ai-indeed.com/encyclopedia/33715.html)

### 4. 方案名：Dify 邮件退款审批模板——小额自动批、大额 LLM 建议+人工邮件拍板 【客服退款·Dify Marketplace·B类·参考架构】

**骨架来源**：Dify Marketplace 官方模板 `Refund Approval by Email with AI Recommendation`（作者 riskey）。模板自带完整工作流节点、`$50` 阈值条件分支与系统提示词骨架。本条在第④⑥段按 Dify 官方实践文档与电商售后业务常识做推导补全，均标注 `# 推导`。

**① 场景与边界**
- 干什么：处理网店的邮件退款申请——小额（模板默认 50 美元以下）自动批准；大额由 LLM 对照退款政策给出建议决策，订单对应的客服主管通过邮件一键批准/拒绝。
- 输入：客户发来的退款请求邮件（含订单信息、退款理由）。
- 输出：小额——自动批准回执；大额——给客服主管的决策建议邮件，附政策依据。
- 不干什么：不做政策协商、不处理不支持的支付渠道的退款、不替代主管做最终决定（大额必须人拍板）。

**② 工具清单**

| 工具 | 作用 | 输入 | 输出 |
|---|---|---|---|

### 1. 方案名：Anthropic Claude Code 团队的 AI 代码评审验证体系——分层自动验证+风险分级人工审批 【研发代码评审·Anthropic·A类方案】

| 工具 | 作用 | 输入 | 输出 |
|---|---|---|---|

| Claude 评审 Agent 组 | 独立上下文复核变更；多个 Agent 独立调查发现项，另一组 Agent 验证 | PR diff | 发现项清单 |
| 安全评审 | 存在未解决问题可阻止合入 | 变更 | 放行/阻止 |
| commit gate | 拦截从未跑过 `/code-review` 或 `/verify` 的提交；off/observe/enforce 三档渐进上线 | 提交事件 | 放行/拦截 |
| rubric 评分 Agent | 独立评分器对照评分细则检查 Claude 的产出（结构化文件生成任务上最高 +10 个百分点） | 产出+细则 | 分数 |

**③ 编排流程**
多 Agent 编排（分层验证+风险分级）：

```text

        → verify skill 真实驱动应用验证（失败 3 轮 → 停止，叫人）
        → 独立上下文复核 Agent → 多 Agent 独立调查发现项 → 另一组验证
        → 安全评审（未解决可阻止合入）
        → 风险分级审批：低风险（文档/旗标内功能）免人工；

```

规则生产闭环：漏报案例 → 三 Agent 尝试反驳候选规则 → 人工 PR 审批进 `REVIEW.md`；flaky 测试不许加 sleep 重试通过，找不到根因就删测试并写明原因。

**④ 关键配置**

```text

REVIEW.md 读取位置=base 分支    # 防 PR 自改评审规则
验证戳=每提交必带（含 none）
评审聚焦=只看新增变更           # 后续轮次不再全文重审
timeout / max_retries（工具级） # 原方案未涉及
```

**⑤ 失败与兜底**
- 检查连续 3 轮失败 → Claude 停止，转人工。
- commit 反复被拦 → 第 2 次被拦后放行下一个提交，避免卡死。

### 3. 方案名：OpenAI Agents SDK 航空客服分流示例——总机分流+专家 Agent+双护栏+转人工 【客服工单分流·OpenAI Agents SDK·B类·参考架构】

**骨架来源**：OpenAI 官方开源示例 `github.com/openai/openai-cs-agents-demo` 与 Agents SDK 官方文档/《A practical guide to building agents》。骨架自带 Agent 图、handoff 机制、护栏代码与转人工链路。第④⑥段按 Agents SDK 默认值与官方指南推导补全，标注 `# 推导`。

**① 场景与边界**
- 干什么：航空客服——分流 Agent 判断意图后移交三类专业 Agent：政策问答（RAG 检索退改签政策）、座位改签（查座位图并改座）、航班状态（查实时动态）；带相关性护栏与越狱护栏；低情感分或复杂问题升级人工（演示中接 Zendesk）。
- 输入：旅客消息（"我的航班晚点了吗""我想换座位"）。
- 输出：政策解答、座位变更确认、航班动态；无法处理时转人工工单。
- 不干什么：不做票价退款执行类高风险操作（指南明确：取消订单、大额退款、支付类动作必须人工介入）；超出示例域的行李、贵宾厅等需求需自行扩展。

**② 工具清单**

| 工具 | 作用 | 输入 | 输出 |
|---|---|---|---|
| 政策检索（RAG） | 检索航司退改签政策原文 | 用户问题 | 政策片段 |
| 航班状态查询 | 返回航班实时动态（如"FLT-456 准点，B7 登机口"） | 航班号 | 状态数据 |
| 座位查询/变更 | 展示座位图并执行改座 | 订单+座位偏好 | 改座结果 |
| 转人工（escalate） | 低情感分/复杂问题升级至人工系统（演示接 Zendesk） | 会话上下文 | 工单 |
| 输入护栏 | 相关性护栏（非航空话题拒绝）+越狱护栏（诱导泄露指令拒绝） | 用户消息 | 放行/拦截 |
| 追踪（Tracing） | 每次 Runner.run 自动生成 trace：模型调用、工具调用、handoff 链、护栏检查 | 运行事件 | 可回放轨迹 |

**③ 编排流程**
多 Agent（分流→专家，handoff 交接，上下文全量保留）：

```text
旅客消息 → 输入护栏（相关性/越狱，与 Agent 并行乐观执行）
        → 分流 Agent 判断意图
        ├─ 政策问题 → 政策 Agent（RAG）→ 回答
        ├─ 改座 → 座位 Agent（查座位图 → 确认 → 改座）
        ├─ 航班动态 → 航班状态 Agent → 回答
        └─ 情感分低于阈值 / 超出能力 → escalate 转人工
        → 全程 trace 自动记录（模型/工具/handoff/护栏）
```

**④ 关键配置**（补全段）

```text
max_turns=10                  # 推导：Agents SDK Runner.run 默认单次运行轮次上限
模型分配：分流/查询用轻量模型，复杂改签用主力模型  # 推导：官方指南建议按复杂度分模型控成本
护栏=乐观并行执行               # 推导：Agents SDK 默认行为，护栏与主 Agent 并发跑
高风险动作（退款/取消）→ 人工    # 推导：官方指南明确的高风险动作清单
温度                           # 原方案未涉及
```

**⑤ 失败与兜底**
- 越界输入（写诗、套提示词）→ 相关性/越狱护栏 tripwire 触发，Runner 抛异常直接拦截，统一话术回复"我只能协助航空出行相关事项"。
- 达到轮次上限或重试阈值 → 按官方指南：超过失败阈值升级人工。
- 高风险操作 → 人工介入触发器（不可逆/高价值动作）。
- 追踪回放 → trace 全量落盘，出问题可精确回放到哪一步判断错。
- 死循环 → `max_turns` 硬上限兜底。

**⑥ 验收指标**（补全段）

| 指标 | 目标值 |
|---|---|
| 分流准确率 | ≥95% # 推算：客服分流属封闭意图集，业务常识目标 |
| 护栏拦截误伤率 | ≤2% # 推算：正常请求被拦即体验事故 |
| 转人工率 | 首期 ≤15% # 推算：分流+专家覆盖主要意图后的人工兜底占比 |
| 单会话成本 | 按 trace 逐会话监控，无目标值 # 原方案未涉及 |

**机会点**：这个示例是中文电商/跨境独立站客服分流最直接的移植底座——fork 官方 Demo、把政策库换成中文退换货规则、handoff 换成国内工单系统，万元级成本两周可见第一个正反馈，比从零写分流稳定得多。

| 工具 | 作用 | 输入 | 输出 |
|---|---|---|---|
| 订单服务 | 订单事实的唯一来源 | 订单引用 | 订单数据（带时间戳与来源 ID） |
| 政策检索索引 | 带版本的政策解释检索 | 问题/提案 | 政策依据（版本化） |
| 确定性校验器 | 资格、所有权、币种、金额上限、历史退款检查 | 提案 | 通过/拒绝 |
| 审批器 | 审批与"精确提案"绑定（不可换提案套用） | 提案+审批人 | 审批记录 |
| 幂等支付操作 | 按 operation ID 执行退款，可安全重试 | 审批记录+operation ID | 支付回执 |
| 动作流水账（action ledger） | 存提案、政策版本、审批、支付操作 ID | 全部关键事件 | 审计与重放依据 |
| 持久运行存储 | 运行状态与队列 | 任务 | 可恢复状态 |

**③ 编排流程**
单工具型 Agent 内嵌固定业务工作流（不上多 Agent）：

```text
认证请求 → API 与运行队列 → 运行时（持久运行状态）
  → Agent（模型+上下文）：解析订单引用 → 检索政策 → 生成解释/退款提案
  → 确定性代码校验：资格、所有权、币种、金额上限、历史退款
  → 审批（与精确提案绑定）→ 独立写能力执行幂等支付
  → 回执与终态校验 → 答复 或 转人工
```

**④ 关键配置**（原文给出假设+补全）

```text
任务量设计=100,000 任务/天      # 原文假设
只读回答目标=15 秒             # 原文假设
并发活跃任务≈150               # 原文按其峰值假设估算
审批任务=异步继续（不等同步响应）
写操作=审批后独立写通道，幂等（按 operation ID）
每租户并发限制=队列+按租户限流
timeout / max_retries / 模型选择 # 原方案未涉及
```

**⑤ 失败与兜底**
- 支付方已扣款但 worker 超时 → 下一个 worker 加载原 operation ID 查询状态，记录原回执而不是再退一笔；状态无法确认 → 挂起进入对账并转人工运营；无证据时绝不告诉客户"退款成功"。
- 重复请求/部分退款/过期政策/跨租户引用/被注入的检索文本/worker 崩溃 → 全部列入评测用例。
- 权限伪造 → 永不从模型提供的客户 ID 推断权限。

**⑥ 验收指标**（补全段）

| 指标 | 目标值 |
|---|---|
| 发布门槛 | 测试套件零未授权写操作 + 预先约定的成功率与延迟目标 # 原文（release gate 示例） |
| 评测方式 | 种子订单库→执行任务→检查终态（正确账户、金额、审批、退款笔数）# 原文 |
| 生产监控 | 持续监控违规，新失败案例回灌测试套件 # 原文 |
| 成功率/延迟具体数值 | 原方案未涉及 |

**机会点**：它把退款失败推演（重复退款、对账、终态校验）写成了可执行的测试用例集——支付服务商和电商中台缺的就是这套"幂等退款"测试资产，第一步把其失败场景翻译成一套开源测试套件（千元级、两周），借它的关注度拿早期用户。

## 本篇机会点小结

**一、最值得动手的一条**：国内 4——Dify 邮件退款审批模板的本地化灰度。理由：它是本篇唯一"骨架现成、改动最小、一周能跑"的方案——自托管 Dify（千元级）+ 接工单系统 + 改政策文本即可上线，先只放小额自动批的量，1-3 个月内用"主管采纳率 ≥85%"验证价值。做给电商客服团队/代运营，第一步是把模板里系统提示词的政策文本换成自己的售后规则。

**二、被验证的需求**：国外 1（Anthropic：90% 代码由 Claude 写/评，一次过率 65%→78%，revert 降 40%+）说明 AI 评审的验证层已在真实生产运转并被大量采用；国外 2（Bretton：年省 24,300 小时、SBA 评审 87% 缩短、$7,500 万 B 轮、MVB Bank 按完成的 AML 案件付费）说明合规 Agent 有人按结果付钱；国内 1（阿里 OCR：六个月 53,900 star、token 成本 1/9~1/15）说明精确率优先的评审工具开发者真会用。

**三、明显的空位**：国内 3 的核保缺件预检——需求写得很清楚（材料完整性检查、要素比对、疑点汇总）但没有任何参数与指标，说明这个单点工具没人做成标准件；国内 2 的 KYA（智能体身份与调用链审计）——架构描述完整但零量化指标，行业标准件缺位；国外 4 的幂等退款失败推演——设计文档里全套测试思路都有，但没有对应的可执行开源测试套件。

**四、本篇结论**：本篇说明 Agent 正在从"演示能力"转向"确定性层兜底+人只签最终字"的工程结构（评审的 commit gate、合规的人工评审环节、退款的审批绑定提案），这一层是当下的共识方向；而参数化配置与量化验收指标在多数公开方案里仍原地踏步——本篇 8 条里有 5 条的④段大面积"原方案未涉及"。
