# 第一部分：国内

### 1. 三层架构客服 Agent：Harness 管工具、Loop 管循环、Graph 管路由 【客服·个人工程实践·DeepSeek+LangGraph】

发布于 11-19/20 前后（页面时间在 48 小时窗口内）。

**① 场景与边界**
- 干什么：面向海外用户的客服 Agent，后端接 DeepSeek，处理 FAQ 知识库问答、订单状态查询、退换货申请三类任务。
- 输入：用户对话消息（含问题描述、订单号）。
- 输出：知识库答复、订单状态与物流信息、已提交的退换货工单。
- 不干什么：不处理与三类任务无关的咨询；退换货在用户明确确认信息前不提交；不直接执行资金操作。

**② 工具清单**
| 工具 | 作用 | 输入 | 输出 |
|---|---|---|---|
| 知识库查询 | 查 FAQ 文档 | 关键词、类目 | 文档片段 |
| 订单查询 | 查订单状态与物流 | 订单号 | 订单状态、物流信息 |
| 退换货申请 | 写工单并触发通知 | 订单号、原因 | 工单结果（带人工确认门槛） |

所有工具入参严格校验；退换货申请额外要求用户明确确认后 Agent 才能提交。

**③ 编排流程**
三层分工：Harness 层注册并校验 3 个工具；Loop 层跑 ReAct 循环，每轮把工具结果摘要（≤200 字）注入上下文；Graph 层用 LangGraph 拆 5 个节点：
```
意图识别 → 信息收集 → 方案匹配 → 执行动作 → 结果反馈
意图识别=软路由：置信度 < 0.7 进澄清节点让用户补充
方案匹配=硬路由：按信息收集的结构化结果选 查询/申请/推荐
```

**④ 关键配置**
```
max_iterations=8      # ReAct 最大迭代轮数
单步 timeout=10        # 秒
工具结果摘要上限=200    # 字
意图置信度阈值=0.7     # 低于则进澄清节点
temperature=0~0.3     # 低温度降低随机性
```

**⑤ 失败与兜底**
- 8 轮未完成 → 自动降级「转人工客服」，附完整对话记录，避免用户被无限拖延。
- 工具入参校验失败 → 拒绝执行，不把任意请求发给业务 API。
- 退换货未经用户确认 → 不提交工单（确定性门槛，不靠提示词）。

**⑥ 验收指标**
| 指标 | 目标值 |
|---|---|
| 成功解决率 | >90%（上线前 <60%） |
| 单次对话成本 | $0.06 上限（上线前 $0.02，三层架构换解决率的主动取舍） |
| 执行轨迹 | 100% 可回溯 |

**机会点**：把这套「Harness/Loop/Graph + 六段参数」做成客服 Agent 的验收模板或迁移服务——给正在自建客服 Agent 的团队按此骨架做审计与改造，第一步先做一份「工具校验/轮数上限/路由兜底」三项体检清单。

来源：http://www.sheratonhq.com/news/191152

### 2. 美团企业版「票来」：四类 Agent 分工收发票，小票审核前置到支付前 【运营·美团企业版·多 Agent 分工】

发布于 2026-11-20。

**① 场景与边界**
- 干什么：企业消费场景的票据收集（单体酒店、民宿无法按月统一开票的催收、识别、验真、归档）与用餐小票合规审核；另覆盖客户咨询、供给运营、差旅（申请、审批、方案推荐、预订、退改）。
- 输入：商家票据（微信/电话渠道）、员工用餐小票、差旅申请。
- 输出：已验真归档的票据、支付前的合规审核结论、差旅预订与退改结果。
- 不干什么：边界由团队明确划定——哪些交给 Agent、哪些节点必须由员工/运营/管理者确认；方案错误、到店无房、退改纠纷等责任环节不交给 Agent 自动处理。

**② 工具清单**
| 工具 | 作用 | 输入 | 输出 |
|---|---|---|---|
| 外呼 Agent | 电话催收票据 | 商家联系方式、账期 | 沟通结果记录 |
| 企微沟通 Agent | 企业微信催票对话 | 商家会话 | 沟通结果记录 |
| 票据识别 Agent | 识别票据信息 | 票据图片 | 结构化票据字段 |
| 验真归档 Agent | 验真并归档 | 结构化票据 | 归档结果（异常转人工） |
| 小票 AI 审核 | 支付前合规校验 | 用餐小票 | 通过/转人工复核 |

**③ 编排流程**
1. 票据收集拆给四类 Agent（外呼 → 企微 → 识别 → 验真归档）串成链，异常情况交人工。
2. 用餐小票：AI 完成初步识别，合规校验前置到支付前；人工只重点复核高风险订单。
3. 差旅：申请 → 审批 → 方案推荐 → 预订 → 退改各环节接 Agent，已与亚信科技试通两个 Agent 的 A2A 交互。

**④ 关键配置**
原方案未涉及（未公开步数上限、超时、重试等参数）。

**⑤ 失败与兜底**
- 票据收集异常 → 转人工处理。
- 小票审核高风险订单 → 人工重点复核（AI 初筛+人工终审双重质控）。

**⑥ 验收指标**
| 指标 | 目标值 |
|---|---|
| 小票 AI 审核通过准确率 | >98% |
| 审核时效节省 | 65% |
| 客服咨询覆盖 | 7×24 小时值守 |

**机会点**：把「四 Agent 收票+支付前合规审核」的分工模式复刻给中小财税服务商——第一步用企微机器人+OCR 给 10 家连锁餐饮/酒店跑通收票验真闭环，按审核准确率收费。

来源：https://3g.china.com/act/finance/13004688/20261120/49890450.html

### 3. 阿里开源 open-code-review：确定性工程层管选文件，LLM 只管判断 【研发·阿里开源 open-code-review·确定性工程+LLM 混合架构·参考架构】

骨架来自哪里：阿里开源项目 open-code-review 的 README/架构文档与自建基准 AACR-Bench（该项目前身是阿里集团内部官方 AI Code Review 助手，两年服务数万名开发者）。本条属 B 类参考架构：原方案六段中②③齐全，④⑥由基准数据与架构约定补全，补全依据均在文中标注。

**① 场景与边界**
- 干什么：对 git diff/commit/全文件扫描做 AI 代码评审，输出行级评论。
- 输入：git diff、commit、全量文件扫描；CI 集成。
- 输出：行级评论 / JSON / SARIF / CI 集成结果。
- 不干什么：不做召回优先的全量报问题（明确「拿召回换精确」）；不做代码修复。

**② 工具清单**
| 工具 | 作用 | 输入 | 输出 |
|---|---|---|---|
| 文件选择与过滤 | 精确决定哪些文件必审 | 变更集 | 待审文件清单 |
| 智能分桶 | 相关文件打包成一个评审单元（如 i18n 中英文 properties 打成 bundle），每个包独立上下文的子 Agent | 待审文件清单 | 评审单元列表 |
| 规则匹配 | 按文件特征套规则（NPE/线程安全/XSS/SQL 注入） | 评审单元 | 命中规则 |
| 代码读取/搜索 | LLM Agent 读完整文件、搜索代码库 | 行号/关键词 | 文件内容、搜索结果 |
| 评论定位+反思模块 | 校验问题位置准不准、内容对不对 | 候选问题 | 定位准确的行级评论 |

**③ 编排流程**
```
输入层(git diff/commit/全文件扫描)
  ↓
确定性工程层(文件选择 → 智能分桶 → 规则匹配 → 评论定位+反思)
  ↓
LLM Agent 层(只做判断: 读完整文件、搜索代码库、生成行级评论)
  ↓
输出层(行级评论 / JSON / SARIF / CI 集成)
```
另有 delegation mode：把文件选择与规则逻辑作为插件贡献给宿主 Agent（Claude Code 等），复用宿主认证与订阅。

**④ 关键配置**
```
分桶策略: 相关文件(如同组 i18n)打成一个 review unit, 每包独立上下文子 Agent  # 原方案约定
Java/Kotlin/C++ 规则文件 security 段: 无, 需自补                        # 原方案未涉及
timeout / max_steps: 原方案未涉及
```

**⑤ 失败与兜底**
- 变更集过大 → 分桶分治稳住大变更集，避免通用 Agent 偷工减料只审一部分。
- 问题位置漂移 → 独立评论定位模块+反思模块二次校验。
- 纯语言 Skills 难调试 → 判断类逻辑收敛进场景化 prompt 与从生产工具调用轨迹蒸馏的工具集。

**⑥ 验收指标**（补全依据：项目自建基准 AACR-Bench，注意是阿里自建、无独立复现）
| 指标 | 目标值 |
|---|---|
| 基准规模 | 50 个开源仓库、200 个真实 PR、10 种语言、1505 个 ground-truth 问题、80+ 高级工程师标注 |
| token 消耗 | 约为通用 Agent 的 1/9（同模型下） |
| Precision/F1 | 明显高于 Claude Code |
| Recall | 主动取舍调低（少报假警报） |

**机会点**：该项目 Java/Kotlin/C++ 规则文件缺 security 段——第一步为这三门语言补 security 规则并回馈上游，再做成企业内网私有化评审发行版卖给对数据不出内网有要求的团队。

### 4. 电商售后工单 Agent：单 Agent 固定管线，三层模型路由把大模型调用压到四成 【客服·电商售后·单 Agent 固定管线+模型分层路由】

页面时间在 11-19~11-21 区间（48 小时窗口内），发布方为自述团队实践。

**① 场景与边界**
- 干什么：电商售后工单自动处理「工单分类 → 查询订单 → 生成回复草稿 → 高风险转人工」一条链。
- 输入：售后工单（编号、用户诉求、历史会话）。
- 输出：工单分类、回复草稿、退款申请（高风险需人工审批）。
- 不干什么：不闲聊、不做营销推荐；只处理售后工单。

**② 工具清单**
| 工具 | 作用 | 输入 | 输出 |
|---|---|---|---|
| 查订单 | 获取订单状态 | 工单关联订单号 | 订单状态摘要 |
| 查物流 | 获取物流信息 | 订单号 | 物流信息 |
| 发起退款申请 | 提交退款 | 订单号、金额、理由 | 退款申请单（前置人工审批） |

**③ 编排流程**
1. 明确不拆多 Agent：单 Agent 走完全流程（每步输入输出清晰，拆两个 Agent 反而多一层自然语言传递开销）。
2. 三层模型路由：入口小模型做意图识别（售后单/物流催单/其他）→ 纯物流催单用规则模板直接回复（不调模型）→ 只有需要生成回复正文时才调大模型。
3. 固定管线执行，状态图管理，退款节点前插入人工审批。

**④ 关键配置**
```
上下文白名单: 工单编号 + 用户诉求前500字 + 订单状态摘要 + 近三轮会话摘要
历史售后记录: 向量库 top3 召回, 不占主上下文
token 预算: 每任务设上限, 超预算直接熔断转人工
回归集: 80 条标注工单
```

**⑤ 失败与兜底**
- 退款操作 → 节点前人工审批，不自动执行。
- token 超预算 → 熔断转人工。
- 观测缺失 → 全程接 Langfuse 记 Trace（每步工具、返回、输出、耗时、token、分支）。

**⑥ 验收指标**
| 指标 | 目标值 |
|---|---|
| 大模型请求占比 | 约四成（路由+模板分流后的实测值） |
| 回归集规模 | 80 条标注工单，上线前全量回归 |
| Trace 覆盖率 | 100%（Langfuse） |

**机会点**：多数电商客服团队缺的不是 Agent 而是「80 条标注回归集」这种验收资产——第一步从历史工单抽样标注做回归集生成工具，按工单类目卖给电商客服 SaaS。

来源：https://kwkr.cn/news/536490

### 1. 订单状态邮件 Agent：只读工具+全量人工复核，按「未编辑率」逐步放开 【客服·邮件工单·只读工具链+人工复核】

发布于 2026-11-19。

**① 场景与边界**
- 干什么：只干一件事——回复「我的订单在哪」类邮件，给出最新物流状态与政策承诺的送达时间。
- 输入：客户邮件（订单号、诉求）。
- 输出：包含追踪状态与政策送达时间的回复（草稿或直接发送）。
- 不干什么：不写任何数据、不改任何系统；不回复其他类型邮件；数据缺失时写 MISSING，绝不估算填空。

**② 工具清单**
| 工具 | 作用 | 输入 | 输出 |
|---|---|---|---|
| 订单查询 | 查订单 | 订单号 | 固定枚举的状态值（不用描述句） |
| 物流追踪 | 查物流 | 订单号 | 追踪状态、送达时间 |
| 政策文档 | 查承诺条款 | 问题类型 | 政策条款 |

全部只读；教训：曾把履约状态以描述句返回，代码把所有描述读成「已发货」，三天扣下 25 封改地址回复、其中 12 单尚未发货——之后改为固定枚举值。

**③ 编排流程**
1. 事实前置：不把整封邮件线程丢给模型，先抽成该案件所需事实（当前诉求/此前承诺/已做动作/缺什么）；25 封线程案例中模型曾漏掉公司已承诺全额退款而自相矛盾，改后修复。
2. 规则单源：同一规则只写一份，全系统引用；曾发现报销规则五处不一致，收敛后才稳。
3. 审批线：事实类与公开政策类问题自动答；花钱/发货类由 Agent 准备、人批准；记录以「人批准的版本」为准。
4. 上线前回放：真实历史案例每例跑两次（模型输出会变）、冻结时效性内容、回放环境禁止写操作。
5. 上线后：全量人工复核，草稿与实发分字段存，用编辑差异定位修复项；某类回复连续无人编辑才允许该类独立发送。

**④ 关键配置**
```
回放次数=2          # 每个历史案例跑两次
输入 token 目标≈4722  # 备件邮件只传相关订单行, 从 37604 降下来
放开标准=某类回复连续未编辑  # 才允许独立发送
自动动作边界=只读工具   # 写操作全部人工
```

**⑤ 失败与兜底**
- 查询空结果与查询失败 → 分开处理（曾因混为一谈导致误报零新客）。
- 模型漏看长期承诺 → 事实前置抽取承诺字段。
- 人工编辑 → 400 份编辑草稿中 53% 删除承诺、22% 补库存状态、10% 用知识库已有答案替换「无信息」，每项对应一个修复。

**⑥ 验收指标**
| 指标 | 目标值 |
|---|---|
| 独立发送量 | 30 天（截至 2026-11-19）3331 封 |
| 人工复核后发送量 | 23120 封 |
| 备件邮件输入 token | 37604 → 4722 |

**机会点**：「未编辑率放开机制」是可复用的产品化缺口——第一步给客服工具链做一个草稿/实发双字段对比组件，输出每类回复的未编辑率曲线，卖给正在谨慎放开 AI 客服的团队。

### 2. Runway「软件工厂」：交付流水线七站逐站交给 Agent，每站先定验收标准 【研发·Runway·云端编码 Agent+AI 评审+摩擦度量】

发布于 2026-11-20。

**① 场景与边界**
- 干什么：把软件交付七个工位（写代码 → 过 CI → 评审 → 批准 → QA → 修故障 → 跑流水线）逐站移交给 Agent，人只在每站验收点介入。
- 输入：任务描述 + 预批准的计划。
- 输出：绿色 PR（过 CI、评审干净）、Agent 评审意见、摩擦地图与改造 brief。
- 不干什么：不自动合并生产变更——批准环节仍保留人审节点（先定每站是否移交、移交后怎么判定结果，再看数据）。

**② 工具清单**
| 工具 | 作用 | 输入 | 输出 |
|---|---|---|---|
| 云端编码 Agent 服务 | 跑编码 Agent 并陪跑到 PR 变绿：写代码→开 PR→重跑 CI→修测试→答评审→rebase | 任务+已批准计划 | 绿色 PR |
| AI 评审 Agent | 与编码 Agent 同上下文（计划+diff+周边代码），往返迭代至干净 | PR+计划 | 评审线程（93% 解决率） |
| 摩擦度量工具 | 从每次 PR 的 Agent 记录测摩擦：实现耗时、评审发现数与严重度、问题回归、变干净时间 | 全部 PR 记录 | 按代码区域标注摩擦的地图+可执行 brief（证据/原因/有界改动/回归测试） |

**③ 编排流程**
```
写代码(编码Agent) → 过CI(自动重跑修复) → 评审(编码Agent⇄AI评审Agent往返)
→ 批准(人/规则批准) → QA → 修故障 → 跑流水线
每站移交前先定该站验收标准; 评审线程不解决则回编码Agent
```

**④ 关键配置**
```
timeout / 步数上限: 原方案未涉及
摩擦基线: 与同规模 PR 对比  # 原方案约定
```

**⑤ 失败与兜底**
- Agent 卡死 → 摩擦地图定位停滞 run 与反复返工区域，配套 brief 交给工程师修路径。
- 访问/凭证不通 → 工程师优先修基础设施（最大的几个收益都来自权限与环境修复）。
- 回归风险 → 用「Agent 批准的更改回退率不高于人工」校准；首轮清理 23 个 PR 后重复行降 16%。

**⑥ 验收指标**
| 指标 | 目标值 |
|---|---|
| Agent 驱动 PR 占比 | 10 月 38%（6 月 0.1%），11 月上半 30% |
| 100 个 Agent PR 无人工提交 | 78 个（11 月上半样本） |
| 首次批准等待中位 | >2 小时 → 约 5 分钟 |
| 周合并 PR | 翻倍以上（月 3000+，7 个仓库） |
| AI 评审线程解决/推动改动率 | 84% → 93% |
| 单次评审成本 | 9 月底重建后降至约 1/3 |

**机会点**：摩擦度量工具（从 Agent 记录自动出「哪里浪费、为什么、怎么修」的地图）在原文是内部工具——第一步做成读 PR/MR 记录输出摩擦报告的独立产品，先适配 GitHub 后适配国内 Git 平台。

### 3. Google Managed Airflow Agent + Data Agent Kit：流水线写 DAG 与故障排查的官方参考架构 【数据·Google Cloud 官方·Airflow Agent+Data Agent Kit·参考架构】

Google Cloud 官方博客发布于 11-19/20（48 小时窗口内）。骨架来自 Google 官方博客与文档：④的关键配置为官方示例明示数值，⑥部分指标按官方示例数值推算并标注。

**① 场景与边界**
- 干什么：数据工程师用 Agent 写/迁移/部署 Airflow DAG；流水线失败后由控制台 Agent 调查失败任务、推荐环境改进、检查 DAG 升级就绪度。
- 输入：自然语言需求描述（含数据源、转换逻辑、幂等与告警要求）；失败任务现场。
- 输出：与目标环境 Airflow 版本对齐的 DAG（先校验环境再写码、部署后确认加载无错）；失败原因与改进建议。
- 不干什么：不替代对部署结果的审查（文中工程师仍逐行 review 生成的 DAG 后才上线）。

**② 工具清单**
| 工具 | 作用 | 输入 | 输出 |
|---|---|---|---|
| Data Agent Kit（Antigravity IDE 插件） | 写、迁移、部署 DAG；写码前先检查目标环境 Airflow 版本 | 自然语言 DAG 需求 | 校验并部署的 DAG |
| Managed Airflow Agent（控制台） | 调查失败任务、推荐环境改进、检查 DAG 是否可升级 | 失败任务/环境信息 | 排查结论与建议 |
| Gemini 模型 | 理解与生成 | 需求+环境上下文 | DAG 代码/诊断 |

**③ 编排流程**
官方示例（零售商点击流，小时级批次）：
```
需求描述 → Agent 检查目标环境(Airflow 2.11.1) → 生成版本对齐 DAG
→ 校验 → 部署到 cymbal-prod → 确认 Airflow 加载无错
DAG 逻辑: 每小时加载上小时事件 → pandas 清洗(嵌套 context 存 JSON 串)
→ 去重 event_id(Pub/Sub 至少一次投递) → 哈希 user_email/ip → 入 BigQuery
失败时邮件 data-oncall
```
故障侧：控制台 Agent 读任务日志、调度器日志、worker 指标定位是代码、数据还是环境问题。

**④ 关键配置**（依据：官方示例明示值）
```
环境: Managed Airflow Gen 3, workers 2 vCPU / 4 GB, autoscale 1~6
落地文件: 每 5 分钟或 128 MB 切一个
Airflow 版本: 2.11.1
幂等: 重跑同一小时不得产生重复(event_id 去重)
```

**⑤ 失败与兜底**
- 反模式（官方明示）：把整小时文件 concat 进单个 DataFrame，忙时每小时约 200 文件/350 MB 会逼近爆内存——改为按文件处理降低内存峰值。
- 任务失败 → 邮件值班人（示例约定）。
- 迁移/升级 → Agent 先检查 DAG 就绪度再动。
- 重跑 → 幂等去重兜底。

**⑥ 验收指标**（前两行为官方示例数值；部署一次通过率为推算值）
| 指标 | 目标值 |
|---|---|
| 忙时输入量 | 每小时约 200 文件 / 350 MB |
| 任务内存峰值 | <2 GB（低于 4 GB worker 上限） |
| 部署一次通过率 | 推算值：>95%（以 Agent 部署后确认加载无错为准） # 推导 |
| 失败定位时长 | 原方案未涉及 |

**机会点**：国内大量自建 Airflow 团队没有等价排查 Agent——第一步做一个读任务日志+调度器日志+worker 指标、输出「代码/数据/环境」三分类归因的开源排查 Agent，先服务私有化 Airflow 用户。

### 4. 争议退款客服 Agent：Anthropic 路由模式 + Temporal Saga 的参考骨架 【客服·争议退款·Temporal+Anthropic 路由模式·参考架构】

骨架来自哪里：Anthropic《Building effective agents》的 routing 模式（其官方示例正是客服分流）+ Temporal 官方 workflow/saga/circuit-breaker/outbox 模式，参考文章为逐层搭建的三路客服退款系统。B 类参考架构：原骨架①②③⑤齐全，④⑥由文章给出的价格数据与确定性模式补全。

**① 场景与边界**
- 干什么：客服三路分流处理：FAQ 问答、「订单在哪」查询、争议退款判定与执行。
- 输入：客户消息。
- 输出：知识库答复、订单状态回复、退款决策与退款执行结果。
- 不干什么：Agent 不碰钱——只读工具出决策，退款由代码（Saga）在规则校验与大额人工批准之后执行。

**② 工具清单**
| 工具 | 作用 | 输入 | 输出 |
|---|---|---|---|
| classify（小模型） | 一次调用分三路 | 客户消息 | faq / where_is_order / refund |
| answer_from_kb | 知识库答复 | 消息 | 答复 |
| track_order_status | 查物流状态 | 订单号 | 状态 |
| agent_loop 只读工具组 | 退款判定：订单状态、规则、客户历史 | 消息+上下文 | 决策提案（不含执行） |
| check_rules | 确定性规则校验（限额、阈值） | 决策提案 | 通过/拦截 |
| wait_for_signal | 大额退款等人工批准 | 审批请求 | 批准/拒绝 |
| refund（Saga） | 幂等执行退款 | 已批准决策 | 退款回执 |
| outbox 事件表 | 订单变更与事件同事务落库 | 订单变更 | 事件发布 |
| OpenTelemetry trace | 每案件全链路追踪 | 运行数据 | Trace（关联 Workflow ID） |

**③ 编排流程**（文章伪代码）
```
kind = classify(message)            # 路由: 一次调用
if kind == "faq":                   # 单次调用答知识库
    answer = answer_from_kb(message)
elif kind == "where_is_order":      # 链: 抽单号→查状态→写回复
    status = track_order_status(message.order); answer = write_reply(status)
else:                               # 争议退款
    decision = agent_loop(message, tools=READ_ONLY_TOOLS)   # Agent 只读
    check_rules(decision)           # 代码校验限额/阈值
    if decision.amount > THRESHOLD:
        approved = wait_for_signal("operator_decision")     # 人工批准
        if not approved: hand_off_to_operator(decision)
    refund(decision)                # Saga 执行, plain code 移动资金
```

**④ 关键配置**（价格行依据文章引用的 2026 年 10 月底牌价；其余为推算并标注）
```
分类模型: 小模型(如 Claude Haiku 5.5)   # 千次分类×2000 input token: $0.23 vs Sonnet 5.5 的 $4.50
退款模型: 强模型                        # 同上依据
max_steps(agent_loop): 原方案未涉及; 推算值: 8~10 步硬上限 # 推导(参照国内第1条同类场景取值)
THRESHOLD: 原方案未涉及, 由业务限额确定  # 推导
幂等键: 每次资金/外部写操作必须携带     # 原方案约定
```

**⑤ 失败与兜底**
- 重试 → 一切工具幂等（幂等键），崩溃重试不产生重复退款。
- 依赖故障 → circuit breaker 熔断外部调用。
- 重试耗尽 → 死信队列（DLQ）。
- 追责 → 每案件 OTel Trace 关联 Temporal Workflow ID，可答「为什么拒了这笔退款」。
- 双写不一致 → transactional outbox：订单变更与事件同事务落库，后台进程发布。

**⑥ 验收指标**（原文给出成本对比；运行类指标为推算值）
| 指标 | 目标值 |
|---|---|
| 分类成本 | $0.23/千次（Haiku 5.5）而非 $4.50（Sonnet 5.5） |
| 退款重复执行次数 | 0（Saga+幂等键） |
| 人工介入率 | 原方案未涉及；推算值：仅金额 >THRESHOLD 的争议单介入 # 推导 |
| Trace 覆盖率 | 100%（OTel GenAI 规范） |

**机会点**：「Agent 只读出决策、代码经规则与人工批准后执行资金」的退款合规骨架在金融客服是硬需求——第一步把该骨架做成支持国内支付/工单系统的开源模板（路由+只读工具+Saga+outbox），附幂等与审批接线说明。

## 本篇机会点小结

**一、最值得动手的一条**：国外第 2 条（Runway 摩擦度量工具）。给谁做：正在大量使用编码 Agent 的研发团队（国内对应 Git 平台生态）。第一步：写一个解析 PR/MR 记录（实现耗时、评审发现数与严重度、问题回归、变干净时间）的脚本，按同规模 PR 基线输出摩擦地图与改造 brief，先开源再商业化。验证周期 1-3 个月——判定标准是能否让某个代码区域的 Agent 返工率可度量下降（Runway 用它做首轮清理后重复行降 16%）。

**二、被验证的需求**：有人已在这一块花钱或赚到钱的证据——国内第 2 条（美团小票 AI 审核准确率 >98%、时效节省 65%，已在真实企业消费链路运行）；国外第 1 条（邮件 Agent 30 天独立发送 3331 封+人工复核 23120 封，规模化运行）；国外第 2 条（38% PR 由 Agent 驱动、首次批准等待 2 小时→5 分钟、月 3000+ PR）；国内第 1 条（解决率 60%→90% 的真实成本换算 $0.02→$0.06）。

**三、明显的空位**：需求存在但没人做好的——国内第 3 条（open-code-review 的 Java/Kotlin/C++ 规则缺 security 段，官方文档自述且基准无独立复现，企业私有化发行版空着）；国外第 3 条（Google 只在自家云提供流水线排查 Agent，私有化 Airflow 用户没有等价物，连失败定位时长这类指标都无人给出）；国外第 4 条（退款合规的「Agent 只读+代码执行」骨架只有参考教程，没有适配国内支付系统的落地模板）。

**四、本篇结论**：今天的 Agent 落地正在从「把模型接上工具」收敛为「把确定性工程放在模型前面」——国内（三层架构、混合架构评审、模型分层路由）和国外（软件工厂逐站移交、Saga 隔离资金操作）都指向同一件事：Agent 的胜负手在边界、验收与兜底，而不是模型本身；还留在原地的是参数化验收（多数方案仍未给出步数/超时/成本上限的可复用默认值）。
