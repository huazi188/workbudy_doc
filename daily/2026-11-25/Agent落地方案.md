# 第一部分：国内 / China

### 1. OpenCodeReview：确定性流水线+Agent 的 AI 代码评审，意见精确到行 【研发·阿里·OCR CLI+Agent】

来源：alibaba/open-code-review 开源仓库与掘金/博客园解读，2026-11-23~25 窗口内的报道（项目 11 月 15 日仍发新版，5 月开源，GitHub 52.1K star）。

**① 场景与边界**
- 干什么：读 Git diff（或用 `ocr scan` 通读存量文件），自动审出问题，输出带文件名+行号区间的结构化审查意见；Agent 可读完整文件、检索代码库、翻其他变更文件补上下文。
- 输入：Git 仓库的 diff 或指定文件/目录；配置一个模型端点。
- 输出：结构化审查意见（文件、行号区间、问题类型，覆盖 NPE、线程安全、XSS、SQL 注入等）。
- 不干什么：不做代码修复与提交；Recall 有意低于通用 Agent——官方明说是「precision 优先于噪音」的取舍，宁可漏报不做噪声放大器。

**② 工具清单**
| 工具/组件 | 作用 | 输入 | 输出 |
|---|---|---|---|
| ocr CLI（依赖 Git≥2.41） | diff 生成、代码搜索、仓库操作 | 仓库/分支/文件 | diff 与文件内容 |
| Agent 工具集（按审查场景调优） | 读完整文件、代码库检索、跨变更文件取上下文 | 审查单元+问题线索 | 深层审查依据 |
| 规则匹配模板引擎 | 按文件特征匹配审查规则，40+ 语言/文件类型 | 文件特征 | 规则集（喂给模型） |
| 定位模块 | 三层渐进式策略把意见钉到具体行 | 模型意见+代码 | 文件+行号 |
| 反思模块 | 拦截幻觉与知识漂移 | 模型意见 | 拦截/放行 |

**③ 编排流程**
```
diff 输入
→ 确定性工程：文件筛选与过滤（不漏文件）
→ 相关文件捆绑成审查单元（如 message_en.properties 与 message_zh.properties 捆绑）
→ 每单元起独立子 Agent（上下文隔离，天然可并发）
→ 模板引擎按文件特征匹配规则喂给模型
→ Agent：风险识别、上下文探索、问题归类
→ 定位模块三层渐进式定位行号
→ 反思模块拦截幻觉 → 输出结构化意见
```

**④ 关键配置**
```
Git >= 2.41          # 硬性依赖
安装：npm install -g @alibaba-group/open-code-review
同模型实测开销：约 38.5 万 token/次、1 分 23 秒
timeout/max_retries：原方案未涉及
```

**⑤ 失败与兜底**
- 大 changeset 通用 Agent 漏审 → 文件筛选用工程逻辑定死，不交给模型自觉。
- 意见行号漂移 → 独立定位模块，不走模型自报行号。
- 提示词抖动导致质量不稳 → 模板引擎匹配规则替代语言驱动。
- `ocr scan` 中断 → `ocr session list` 查会话，`--resume` 续扫。

**⑥ 验收指标**
| 指标 | 目标值 |
|---|---|
| F1（AACR-Bench，Claude Opus 4.6 挂载） | 25.1%（裸跑 11.6%） |
| Precision | 33.9% |
| 平均 token | 38.5 万（裸跑 566 万，约 1/9） |
| 单次审查耗时 | 1 分 23 秒（裸跑 13 分钟） |

基准库 AACR-Bench：50 个开源仓库、200 个真实 PR、10 种语言、80+ 资深工程师标注 1505 个标准答案问题，数据集公开在 HuggingFace 可复验。

**机会点**：开源即用、验证极快——给没用起来的研发团队做「接入 CI + 用历史 PR 同口径评测」的落地服务，第一步挑 10 个真实历史 PR 按官方基准跑一次对比。

### 2. ChatBI 金融多 Agent：取数问答与异常归因，置信度低于 0.85 必须人工介入 【数据·数势科技/滴滴ChatBI·DeepSeek/Qwen】

来源：数势科技公开文档与腾讯 OlaChat 实例代码的转述（经窗口内技术文章收录）。

**① 场景与边界**
- 干什么：金融业务自然语言取数、衍生指标生成、趋势归因、报告生成。
- 输入：自然语言取数/归因问题（如「华东区销售额为何下降」）。
- 输出：指标值、带置信度的归因结论、Markdown+ChartJS JSON 报告。
- 不干什么：不接触原始表名（Metric Agent 输入必须是语义层 ID）；置信度<0.85 的归因不直接输出；具体 SQL 的 WHERE/JOIN 由封装 API 决定，模型不许自由生成。

**② 工具清单**
| 工具 | 作用 | 输入 | 输出 |
|---|---|---|---|
| `get_sales_by_province(province, time_range)` 等封装 API | 权限校验（实时 LDAP）、时间标准化、分片路由、业务规则注入（如车险扣除退保金额） | 省份+时间范围 | JSON 结果 |
| output_schema_validation 中间件 | 强制报告输出合法 Markdown/ChartJS JSON Schema | 模型输出 | 校验后结构 |
| 语义层 ID 目录 | 指标定义与血缘 | 指标查询 | 语义层 ID |
| 人工复核开关 | ETL 产物抽检 | ETL JSON 质量报告 | 放行/打回 |

**③ 编排流程**
```
问题 → ETL Agent（DeepSeek V3 蒸馏版：清洗、异常检测、JSON 质量报告）
→ Metric Agent（DeepSeek R1 全参：衍生指标生成、血缘追踪，只认语义层 ID）
→ Insight Agent（Qwen72B 自研：趋势/异常维度，输出必须带置信度）
→ Report Agent（DeepSeek R1：限定模板生成报告）
```
核心逻辑：模型只负责「推理规划」（先查什么、按什么分组），精确执行全部交给封装 API。

**④ 关键配置**
```
置信度阈值 = 0.85        # Insight Agent 输出闸门，低于即人工介入
ETL 模型 = DeepSeek V3 蒸馏版   # 仅处理原始数据
指标/报告模型 = DeepSeek R1 全参
归因模型 = Qwen72B 自研
步数/超时/重试：原方案未涉及
```

**⑤ 失败与兜底**
- V3 把 NULL 误判为 0 污染训练数据 → 加人工复核开关。
- R1 直接写 SQL 跨库查询失败 → 禁止接触原始表名，只给语义层 ID。
- 小模型归因准确率仅 63% → 改为只输出异常维度（如「华东区、A 产品」），归因结论交给业务规则引擎。
- R1 生成含 HTML 标签的报告致移动端渲染崩溃 → 强制 output_schema_validation 中间件。
- 模型编造参数（如把逾期天数传成应还金额的教训）→ 工具网关层再做参数 schema 校验，范围、类型、边界全部卡死。

**⑥ 验收指标**
| 指标 | 目标值 |
|---|---|
| 归因置信度闸门 | <0.85 一律人工介入（原方案口径） |
| 小模型直接归因 | 已禁止（实测准确率仅 63% 不达标） |
| 任务完成率/成本等 | 原方案未涉及 |

**机会点**：「权限内嵌的取数 API 封装」是所有 ChatBI 落地的真堵点（权限、监管规则、分片路由模型学不会）——做一家企业的语义层+API 封装实施，第一步挑 5 个高频取数问题封装成带权限校验的 API 再接 Agent。

### 3. 客服 Agent 工程化六层架构：退款/改地址/开发票三类高频任务独立完成率 70% 起步 【客服·自研团队·六层混合架构】

来源：窗口内发布的客服 Agent 交付实录（技术专栏文章，声称来自真实交付对齐）。

**① 场景与边界**
- 干什么：消化标准化程度高的客服会话——退款申请、地址修改、发票申请三类高频任务。
- 输入：多渠道用户消息（微信/App/Web 统一抹平成同一套消息协议）。
- 输出：任务执行结果；处理不了时无感转人工，且转接前上下文完整带过去。
- 不干什么：复杂客诉、情绪化对话、需要人工判断的会话不做，留给真人。

**② 工具清单**
| 工具 | 作用 | 输入 | 输出 |
|---|---|---|---|
| Function Calling 网关+工具注册中心 | 对接订单/退款/发票等业务系统执行操作 | 结构化意图+槽位 | 业务系统返回 |
| 状态机引擎 | 任务状态流转（哪些节点必须走，代码说了算） | 识别结果 | 状态迁移 |
| 意图分类小模型 | 核心意图识别，与大模型多路并行兜底 | 用户消息 | 意图+槽位 |
| 向量数据库 | 历史会话检索、用户画像 | 会话 ID/查询 | 相关历史 |
| Trace 系统+离线评测流水线 | 全链路追踪、会话回放、质检 | 全量调用 | 评测报告 |

**③ 编排流程**
```
入口层（渠道适配、会话 ID 统一映射）
→ 编排层：意图识别 → 策略决策 → 状态机流转
  （原则：识别到退款意图后必须走哪几个状态节点由代码控制，不交给模型自由发挥）
→ 工具层：Function Calling 执行具体操作
→ 记忆层：会话级记忆 + 向量检索历史
→ 模型层：大模型生成 + 意图小模型 + 安全审核模型多路并行
→ 可观测层：全链路 Trace、回放、离线评测
→ 低置信度/用户要求人工 → 无感转接（上下文完整移交）
```

**④ 关键配置**
```
max_steps/timeout/max_retries：原方案未涉及
模型编组：大模型（生成）+ 意图分类小模型 + 安全审核模型，三路并行
```

**⑤ 失败与兜底**
- 意图置信度不足 → 兜底转人工。
- 用户明确要求人工 → 立即无感转接。
- 语义理解错误风险 → 模型选型+多路并行兜底架构。
- 模型自由发挥导致流程失控 → 状态流转硬编码。

**⑥ 验收指标**
| 指标 | 目标值 |
|---|---|
| 核心意图识别准确率 | ≥95% |
| 关键槽位（订单号/商品/地址）抽取准确率 | ≥90% |
| 三类高频任务 Agent 独立完成率 | ≥70% |
| 转人工 | 无感转接，上下文完整带过去 |

**机会点**：所有客服 Agent 都卡在「转人工时上下文怎么完整移交」——把交接包（会话摘要+槽位+已执行动作）做成对主流客服系统（如智齿、网易七鱼）的标准件，第一步挑 1 家客服 SaaS 做对接插件。

### 4. Dify 智能投诉处理工作流：意图 5 类×情绪 3 档的路由矩阵，退款+愤怒直接标 P0 【客服投诉·Dify·参考架构】

**B 类说明**：骨架来自 Dify 工作流的可视化编排能力（开始/代码/LLM/条件分支/HTTP/知识库检索节点）与窗口内的投诉处理实战文；本条补全④⑥段，依据为 Dify 官方默认配置惯例与文中业务常识推算，逐项标注。

**① 场景与边界**
- 干什么：把自由文本投诉转成结构化工单——分类、情绪定档、抽取要素、按严重程度路由到业务系统。
- 输入：3 个固定入参 `user_id`、`text`、`channel`（原文明确要求入参尽量少而稳定，可选参数越多校验越复杂）。
- 输出：工单分类（退款/换货/物流/质量/服务态度五类）、情绪档位（平静/不满/愤怒三档）、结构化 JSON（订单号、商品名、问题描述、期望方案）、工单编号。
- 不干什么：不做安抚回复（提示词限定为「售后工单解析助手」，只做抽取和分类）；不自动赔付。

**② 工具清单**
| 工具/节点 | 作用 | 输入 | 输出 |
|---|---|---|---|
| 代码节点 | 订单号正则提取 | text | 订单号 |
| LLM 节点 | 意图分类（5 类）+情绪判断（3 档），提示词含角色/输入范围/输出格式/边界条件四段 | text+订单号 | 结构化分类结果 |
| 条件分支节点 | 按严重程度分流（退款类且愤怒→P0，通知值班主管） | 分类+情绪 | 路由分支 |
| HTTP 请求节点 | 推送结构化工单到业务系统 | JSON | 工单号 |
| 知识库检索节点 | 退换货规则、物流赔付标准等政策检索（替代硬塞上下文） | text | 政策片段 |

**③ 编排流程**
```
开始(user_id, text, channel)
→ 代码节点：正则提取订单号
→ LLM 节点：五类意图 + 三档情绪
→ 条件分支：严重程度分流（退款+愤怒 → P0 + 值班主管）
→ HTTP 节点：结构化工单推送业务系统
→ 结束：返回工单编号
```

**④ 关键配置**（# 推导 补全）
```
入参 = user_id/text/channel 三项      # 原文明确要求
知识库检索 Top K = 3                 # 同窗口 Dify 智能客服示例的配置
temperature = 0                      # 推算值：结构化抽取任务常规设定，原方案未涉及
节点超时/重试：原方案未涉及
```

**⑤ 失败与兜底**
- 检索无结果 → 条件分支记录未受理（窗口内 Dify 工作流模板的标准做法）。
- LLM 输出非结构化 → 提示词四段式（角色/输入范围/输出格式/边界条件）+ 逐节点查看中间结果定位。
- 排查困难 → Dify 节点级日志天然记录每节点输入输出，直接看异常节点入参出参。
- 拆分过度 → 原文反例：把「利率查询」拆成三个 Agent，每次请求多等两轮调度，延迟直线上升；单 Agent 能跑通的线性任务不拆。

**⑥ 验收指标**（# 推算）
| 指标 | 目标值 |
|---|---|
| 意图分类准确率 | ≥90%（推算值） |
| 工单路由错误率 | <5%（推算值） |
| P0 送达 | 即时推送值班主管（原方案口径） |

**机会点**：五类×三档×P0 的路由矩阵是中小电商普遍缺的现成件——做成可导入的 Dify DSL 模板包发布，第一步把这套骨架整理成一条可直接导入测试的工作流模板并开源。

### 1. Bitmovin 多 Agent 客服：Zendesk 工单自主解决，四类子 Agent 分工+置信度转人工 【客服工单·Bitmovin·Google ADK】

来源：Bitmovin 工程博客（窗口内 The Agent Times 收录解读）。A 类，真实上线于生产环境。

**① 场景与边界**
- 干什么：自主分诊并解决 Zendesk 常规技术工单——查内部文档、诊断 Bitmovin Player 与编码产品问题、直接回帖给客户。
- 输入：Zendesk 来的客服工单。
- 输出：直接回复客户的解决方案，或内部处理摘要。
- 不干什么：置信度不够不硬答——handoff agent 负责把不达标的工单升级给人工。

**② 工具清单**
| 工具 | 作用 | 输入 | 输出 |
|---|---|---|---|
| Vertex AI Search | RAG 检索内部 SOP 与知识库 | 工单问题 | 相关文档片段 |
| Google Search grounding | 外部上下文（如第三方服务故障状态） | 查询 | 外部信息 |
| Zendesk API | 读工单、回帖 | 工单 ID+内容 | 工单状态 |
| Bitmovin 产品诊断知识 | 编码与播放器问题诊断 | 错误描述 | 诊断结论 |

**③ 编排流程**
```
Zendesk 工单 → root orchestrator（根编排 Agent）
→ documentation agent：RAG 查 SOP 与知识库
→ technical agent：诊断编码/API 问题
→ search agent：查外部来源（第三方故障等）
→ 汇总结果 → 直接回复客户
→ 置信度不达标 → handoff agent 升级人工
```

**④ 关键配置**
```
框架 = Google ADK（late 2025 由单 RAG 应用重构为多 Agent，2026 年初上线）
模型/检索 = Vertex AI Search + Google Search grounding
置信度阈值数值：原方案未涉及
步数/超时/重试：原方案未涉及
```

**⑤ 失败与兜底**
- 置信度不达标 → handoff agent 转人工（架构级兜底，数值未披露）。
- 演进路径即风险控制：2024 先上简单 RAG 原型验证，2025 年用 Cursor/Claude Code 提效开发，late 2025 重构为 ADK 多 Agent 才上生产——两年渐进，不是一步到位。

**⑥ 验收指标**
| 指标 | 目标值 |
|---|---|
| 任务完成率/转人工率 | 原方案未涉及（仅称 routine tickets 可无人介入） |

**机会点**：ADK+Vertex Search 的客服分诊骨架可复刻，但该方案没公开参数与指标——给用 Zendesk/Gorgias 的团队做 ADK 复刻实施，第一步挑 20 个历史工单建黄金评测集再动架构。

### 2. ADK 单 Agent 参考架构：bug 报告自动分诊（查重+收集上下文+建单） 【研发缺陷分诊·Google·参考架构】

**B 类说明**：骨架来自 Google Cloud 官方参考架构文档《Single-agent AI system using ADK and Cloud Run》（官方给出的用例即 Automated bug report triage）；本条补全④⑥段，逐项标注依据。

**① 场景与边界**
- 干什么：bug 报告自动分诊——理解问题、搜索重复报告、收集相关技术上下文、在系统中创建 bug。
- 输入：用户/工单系统提交的 bug 报告文本（聊天前端）。
- 输出：新建的 bug 单（含查重结论与技术上下文）。
- 不干什么：不修复 bug；只做初步调查，复杂问题交人工专家（官方文档定位为「让人类专家聚焦复杂问题」）。

**② 工具清单**
| 工具 | 作用 | 输入 | 输出 |
|---|---|---|---|
| MCP Toolbox for Databases | 数据库工具（连接池、鉴权、可观测性由它管） | 工具调用 | 结构化查询结果 |
| Google Search 内置工具 | 外部信息 grounding | 查询 | 外部结果 |
| Model Armor | 提示注入/PII/有害内容过滤（入向+出向全量） | 每次模型请求 | 掩码/拦截结果 |
| bug 系统接口 | 创建/查重 bug 单 | 结构化报告 | bug ID |
| Cloud Observability | 日志、监控、全链路 tracing | 全量运行 | 可观测数据 |

**③ 编排流程**
```
用户提交报告（Cloud Run 前端）
→ Agent → 推理请求先过 Model Armor（PII 掩码、注入拦截）
→ Gemini 判断调用哪些工具（查重、取上下文）
→ 工具结果进上下文 → grounding + 中间校验
→ 回写 bug 系统 → 返回用户
```

**④ 关键配置**（# 推导 补全）
```
部署 = Cloud Run（可换 GKE / Gemini Enterprise Agent Platform）
模型 = Gemini（Gemini Enterprise Agent Platform 推理）
安全 = Model Armor 全量过滤（官方架构必配项）
temperature = 0                # 推算值：分诊分类任务常规设定，原方案未涉及
步数上限/超时/重试：原方案未涉及
```

**⑤ 失败与兜底**
- 恶意输入/注入 → Model Armor 直接拦截或掩码（官方设计）。
- 数据库连接复杂度（池化、鉴权）→ 由 MCP Toolbox 承接，Agent 不直连。
- 死循环兜底：原方案未涉及。

**⑥ 验收指标**（# 推算）
| 指标 | 目标值 |
|---|---|
| 分诊准确性/查重命中 | 原方案未涉及（只定性称「显著加快初研与上下文收集」） |
| 人工复核率 | <30%（推算值：分诊类任务常识目标） |

**机会点**：官方架构缺验收件——参照社区 adk_eval_starter 的做法（Pytest+ADK CLI 双评测通道），给用 Jira/GitHub Issues 的团队出「分诊 Agent 部署包+评测集」，第一步用官方示例对一个真实仓库跑通查重+建单。

### 3. eMondrian MCP：自然语言直出带实时透视表的 Excel，权限按调用者角色裁剪 【数据报表·eMondrian·MCP·参考架构】

**B 类说明**：骨架来自 eMondrian MCP server 官方工具定义与 dev.to 实测文章（2026-11 窗口内发布）；本条补全④⑥段，依据为文中实测数据与 MCP 规范惯例，逐项标注。

**① 场景与边界**
- 干什么：把「分析师开 Excel 连 OLAP 拖字段」变成一句话——Agent 在语义模型上生成 .xlsx，内含 live PivotTable，刷新即取最新数。
- 输入：自然语言报表需求（如「按年列航班量、取消率、平均到达延误」）。
- 输出：普通 Excel 工作簿（含 XMLA 实时连接、行列层级/筛选/度量、来自模型的数字格式），文件不带数据不带凭据。
- 不干什么：不在服务端写任何数据；不生成带凭据的文件；只生成调用者角色可见的层级/度量/成员。

**② 工具清单**
| 工具 | 作用 | 输入 | 输出 |
|---|---|---|---|
| `list_catalogs` | 列出语义模型目录 | — | 目录列表 |
| `describe_cube` | 按业务名列出 cube、层级、度量 | catalog | 结构描述 |
| `make_excel_pivot` | 生成带 live PivotTable 的 xlsx | catalog/cube/rows/cols/filters/measures | xlsx 文件 |

**③ 编排流程**
```
用户一句话需求
→ Agent 调 list_catalogs 找模型
→ 调 describe_cube 看层级与度量（按业务名）
→ 组装 make_excel_pivot 参数（如 rows=["[Time.Year]"], measures=["[Measures].[Flights]",...]）
→ 服务端生成工作簿（读模型按调用者 roles 裁剪）→ Agent 保存到本地
→ 用户打开 Excel 按 Refresh All 取实时数
```
实测例：OnTime 目录（182,315,946 条航班）按年透视，取消率 1.90%、平均延误 12.58 分钟，1987 年 1,311,826 架次、2024 年 7,079,061 架次；工作簿约 5KB。

**④ 关键配置**（# 推导 补全）
```
协议 = MCP（XMLA 端点，eMondrian 社区版含 Keycloak 认证网关）
权限 = 按调用者 roles 裁剪可透视的层级/度量/成员
文件体量 ≈ 5KB 量级（不带数据）
timeout/重试/步数上限：原方案未涉及
```

**⑤ 失败与兜底**
- 模型定位错 → 先 list_catalogs 再 describe_cube，两步确认后才生成。
- 越权 → 服务端按调用者 roles 只生成可见成员，Agent 层无法绕过。
- 刷新失败 → Excel 端走 XMLA 连接重取；原方案对 Agent 循环上限未涉及。

**⑥ 验收指标**（# 推算）
| 指标 | 目标值 |
|---|---|
| 数字正确性 | 与 MDX/Power BI 查询结果一致（原文测试口径：刷新后全部对齐） |
| 生成成功率 | ≥95%（推算值：报表生成类任务常识目标） |

**机会点**：存量 OLAP/语义模型客户几乎没人做这层 MCP 适配——给用 Analysis Services/eMondrian 的企业做接入，第一步接 1 家客户的真实模型，用 3 个高频报表做对比试点。

## 本篇机会点小结

**一、最值得动手的一条**：国内第 1 条（OpenCodeReview 接入服务）。它是本篇唯一开源即用、且有公开基准可复验的方案：不用写架构，把 `ocr` CLI 接进团队 CI，用 10 个真实历史 PR 按官方 AACR-Bench 同口径跑一次 F1/token 对比，2 周内就能拿到「值不值得全面替换通用 Agent 评审」的结论。启动成本千元级（就是 token 费），验证周期 2 周。

**二、被验证的需求**：国内第 1 条——阿里内部跑了两年、服务数万开发者、识别数百万缺陷，半年攒 52.1K star，说明企业真在为「评审质量+token 成本」付钱（官方口径，token 数据可复验）；国内第 2 条——滴滴 ChatBI 金融场景已落地多 Agent 分工，且失败案例（NULL 误判、63% 归因准确率）真实到能当反例教材，说明踩坑成本已被市场承认；国内第 3 条——意图准确率 95%/完成率 70% 是「双方对齐后的验收口径」，说明甲方已经开始按合同数字验收 Agent；国外第 1 条——Bitmovin 用两年从 RAG 原型走到 ADK 多 Agent 上生产，自主解决 Zendesk 常规工单。

**三、明显的空位**：国外第 2 条——Google 官方参考架构连一个验收指标都没给（只说「显著加快」），分诊类 Agent 的评测 starter 是空白；国外第 1 条——Bitmovin 方案全程未披露置信度阈值与转人工率，客服 Agent 公开方案普遍缺口径，谁能把「黄金工单评测集」做成标准件谁就补上了这个洞；国内第 4 条——投诉路由矩阵（5 类×3 档×P0）在 Dify 生态里只有教程没有可直接导入的模板包；国外第 3 条——语义模型直出 Excel 透视表这类老分析师工作流的 MCP 适配，实测文章之外几乎无人跟进。

**四、本篇结论**：这个领域的方案正在从「拼 Agent 数量和框架」转向「确定性工程卡流程+权限闸门卡输出」（第 1、2 条的混合架构、第 2 条的置信度硬闸门都是同一信号），但七个方案里四个没给量化验收指标——「怎么判断做成了」仍然大面积留在原地，这既是缺口也是下一步的生意。
