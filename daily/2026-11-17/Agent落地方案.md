# 第一部分：国内 / China

### 1. AIBI 问数归因 Agent：先取可信数据，再决定要不要找原因 【数据·每日互动·Agent+Workflow+Tool】

**① 场景与边界**

- 干什么：业务负责人提出「本周数据如何，如果有异常再找原因」这类分析任务，Agent 先确认业务口径、定位指标与数据，调用 SQL 生成与执行能力取数，再根据结果决定是否进入归因分析。
- 输入：自然语言分析问题（指标 + 时间范围 + 判断标准）。
- 输出：本周与上周对比数据、变化幅度和判断依据；存在异常时输出按渠道/人群/关键触点拆解的归因报告。
- 不干什么：任务停在可信事实上，不额外分析；标准不明确时请求负责人补充判断标准，不自行猜测口径。

**② 工具清单**

| 工具 | 作用 | 输入 | 输出 |
| --- | --- | --- | --- |
| 问数 Tool（SQL 生成与执行） | 按受治理指标查询经营数据，内置权限校验与安全控制 | 指标 + 时间范围 | 本周/上周可比较数据 |
| 分析 Tool | 按渠道、人群或关键触点展开归因，按既定步骤组织证据 | 归因目标 + 受治理指标 + 数据表引用（原样传入） | 归因报告 |
| 企业指标知识库 | 同一份指标定义既帮问数确认口径，也帮分析解释波动 | 指标定义/活动说明 | 口径与证据引用 |

**③ 编排流程**

```
用户问题 → Agent 确认业务口径 → 问数 Tool 取数
  ├─ 无异常 → 依据规则与问数证据交付对比数据和变化幅度，停止
  ├─ 标准不明确 → 请求负责人补充判断标准（转人工）
  └─ 有异常 → 按分析契约构造归因目标，把受治理指标与数据表引用
              原样传入分析 Tool → 归因报告
任何一步失败：根据 reason 补足条件或调整路径，保留已取得的可用结果，不从头发跑
```

多 Agent 拆分：Agent 只编排业务动作，各 Tool 内部保留确定性 Workflow（查询走权限校验，分析走既定步骤）；依赖通过无状态设计显式传递。

**④ 关键配置**

```
原方案未涉及具体步数/超时/温度数值；架构原则为无状态设计、依赖显式传递、知识与数据引用可复用
```

**⑤ 失败与兜底**

- 某一步失败 → 根据 reason 决定补足条件或调整路径，保留前面已取得的可用结果，而不是整条任务从头开始
- 判断标准不明确 → 停止并请求负责人补充，不猜

**⑥ 验收指标**
原方案未涉及具体数值。

**机会点**：问数与归因两段拆分、局部失败可单独处理的架构是可直接抄的骨架——给中小企业数据团队第一步把「口径确认+取数」封装成可复用 Tool，在自有数仓上复刻这套分层。

来源：https://www.csdn.net/article/2026-11-16/170865044

### 2. Open Code Review：确定性工程包住 Agent 的代码评审 【研发·阿里巴巴开源·Go CLI+LLM Agent】

**① 场景与边界**

- 干什么：读取 Git diff，产出带行级精度的结构化评审评论（也可 `ocr scan` 审查整个文件）；LLM 只负责判断，选文件、分组、规则匹配、定位校验全部由确定性代码完成。
- 输入：Git diff（或提交区间/单个文件）。
- 输出：带行号定位、可追溯的结构化评审评论。
- 不干什么：不追求全覆盖高召回——宁可漏掉部分真实缺陷，也不给开发者刷屏（官方明说 recall 更低是有意取舍）。

**② 工具清单**

| 工具 | 作用 | 输入 | 输出 |
| --- | --- | --- | --- |
| 文件选择器（确定性） | 决定哪些变更文件被评审、哪些被过滤，避免大变更集漏审 | diff | 待评审文件列表 |
| 分组器（确定性） | 相关文件打包为一个评审单元（如 message\_en.properties 与 message\_zh.properties 同审） | 文件列表 | 评审 bundle |
| 规则模板引擎 | 按模板匹配内置规则集（空指针、线程安全、XSS、SQL 注入），不靠模型挑规则 | bundle | 适用规则 |
| 定位模块 + 反思模块 | 校验每条评论落在正确行、内容是否站得住 | 评论草稿 | 修正后评论 |
| Agent 工具集（从生产工具调用轨迹蒸馏） | 读完整文件内容、搜索代码库、拉取其他变更文件作上下文 | 模型决策 | 上下文证据 |

**③ 编排流程**

```
diff → 文件选择（确定性）→ 分组（确定性）→ 每个 bundle 一个上下文隔离子 Agent（可并行）
→ 规则模板匹配 → Agent 读文件/搜索代码库做判断 → 定位校验 → 反思 → 汇总输出评论
```

单/多 Agent：多 Agent，每个 bundle 独立子 Agent，隔离上下文保证大变更集稳定。

**④ 关键配置**
原方案未涉及具体步数/超时数值；配置面为模型端点（OpenAI/Anthropic 兼容）与四种审查模式（diff/分支区间/提交/全文件）。

**⑤ 失败与兜底**

- 覆盖不全 → 确定性文件选择器兜底，禁止模型抄近路
- 位置漂移 → 独立定位模块校验行号/文件引用
- 质量波动 → 规则由模板引擎匹配而非模型自选，反思模块复核内容
- 噪声问题 → 以低召回换高 precision，避免 CI 里每条噪声评论消耗人工分诊

**⑥ 验收指标**

| 指标 | 结果（官方基准） |
| --- | --- |
| Token 消耗 | 约为同模型通用 Agent 的 1/9 |
| Precision / F1 | 高于同模型通用 Agent |
| Recall | 低于通用 Agent（有意取舍） |
| 基准规模 | 50 个开源仓库、200 个真实 PR、10 种语言、80+ 工程师交叉验证、1505 个标注问题 |
| 生产验证 | 内部服务约两年、服务数万名开发者 |

**机会点**：「确定性工程 × Agent」的分工模式（流程硬约束交给代码，判断留给模型）可复制到任何审核类 Agent——第一步把目标业务的规则清单做成模板引擎规则集，再让模型只做语义判断。

来源：https://github.com/alibaba/open-code-review （解析见 [http://www.wmrh.cn/news/8364](http://www.wmrh.cn/news/8364) ）

### 3. 制造业报价利润预审 Agent：把亏损单拦在报价签约前 【销售/财务·制造业业财连载·Dify+DeepSeek】

**① 场景与边界**

- 干什么：销售上传报价台账与多层 BOM，Agent 自动解析 BOM 滚算成本、对照毛利红线测算、识别低毛利风险、输出《报价毛利预审简报》供评审。
- 输入：报价台账 Excel + BOM 清单 Excel（两个文件变量）。
- 输出：五段式预审简报（基础信息、成本拆解、毛利结果、风险判定、优化建议）。
- 不干什么：只读不写——不修改 BOM、不生成 ERP 单据、不自动拦截/自动审批，风险结论只作提示，人工终审保留；BOM 常年固定、毛利稳定的企业不需要（Excel 即够）。

**② 工具清单**

| 工具 | 作用 | 输入 | 输出 |
| --- | --- | --- | --- |
| 双文档提取器（并行 A/B） | 分别解析报价台账与 BOM（合并提取会字段混淆导致滚算出错） | quote\_file / bom\_file | quote\_content / bom\_content |
| LLM 查询改写节点 | 把复杂业务需求精简为 2-3 条检索短句，解决长文本召回空白 | 用户分析需求 | search\_query |
| 知识检索节点 | 检索「报价评审制度库」（毛利红线、费用分摊、损耗规则、特批要求） | search\_query | knowledge\_result（制度条款） |
| LLM 主测算节点 | 按固定公式逐层测算物料/人工/制造费用/杂费，判定风险 | 台账+BOM+制度条款 | final\_report（预审简报） |
| 知识库「报价评审制度库」 | 承载《销售报价及毛利评审管理规范》 | 制度文本 | 检索条款 |

**③ 编排流程**

```
用户上传报价台账 + BOM Excel
→ 双文档提取器（并行，A 解析台账 / B 解析 BOM）
→ LLM 查询改写（生成检索短句）
→ 知识检索（报价评审制度库）
→ LLM 主测算（毛利测算 + 风险识别）
→ 结束节点输出预审简报 → 销售/财务评审 → 人工审批 → ERP 下单、PLM 锁定 BOM 版本
```

**④ 关键配置**

```
知识库分段大小=300
召回条数=3
相似度阈值=0.65
索引模式=经济模式
模型=DeepSeek（私有化部署优先，敏感成本数据不出本地）
知识库权限=只开放财务 BP、报价评审负责人；普通销售只能运行 Agent
```

**⑤ 失败与兜底**

- BOM 成本没滚算到底层原材料/半成品重复叠加 → 主测算提示词强制「按固定公式逐层测算、不编造数据」，缺数据或缺制度时按标注口径提示
- 知识库召回为空 → 切换经济模式、适当调低相似度阈值
- 知识库选不到 → 确认工作空间一致、索引完成
- 数据泄露 → 私有化 Dify 部署、对外简报可配置脱敏版本（隐藏原材料单价，只留毛利率与风险结论）、全链路操作日志留痕

**⑥ 验收指标**

| 指标 | 目标值（官方测试用例） |
| --- | --- |
| 毛利率达标单 | 正常评审，不出风险标记 |
| 毛利率低于红线 12% | 标记低毛利风险、提示特批 |
| 测算耗时 | 替代人工单次 30 分钟以上的手工测算（原方案未给出 Agent 端具体耗时数值） |

**机会点**：作者已放出全套可复用素材（报价台账模板、带测试数据的多层 BOM、制度文本、全套提示词）——给制造业财务顾问/交付商第一步直接拿这套素材给一家装备制造企业试点，两周内即可用「拦下几笔低毛利单」验证价值。

### 4. 多模态 + 工具调用客服方案：从「看懂一张单据」到「在系统里把活干完」 【客服·企业客服系统·多模态+工具调用四层】

**① 场景与边界**

- 干什么：打通「看懂一张单据、听完一段录音、再到系统里把结果填进去」的链路——多模态把非结构化输入转成可处理信息，工具调用把动作编排到具体业务系统。
- 输入：图片、扫描件、文档、语音（客服工单相关的非结构化材料）。
- 输出：结构化文本 + 白名单内系统操作结果（查询、填单、归档）。
- 不干什么：模型只给初稿与初筛结果，最终提交仍需人确认；写入类操作单独授权，不做无人终审的自动化。

**② 工具清单**

| 工具 | 作用 | 输入 | 输出 |
| --- | --- | --- | --- |
| 输入层（OCR/ASR + 字段抽取） | 格式归一、转写、字段抽取 | 图片/文档/语音 | 结构化文本 |
| 编排层 | 任务拆成可枚举步骤，明确每步入参/出参/失败分支 | 结构化文本 | 步骤序列 |
| 执行层工具（白名单） | 查询、填单、归档；读操作与写操作分开配置 | 步骤入参 | 系统操作结果 |
| 复核层 | 产出落草稿态，保留关键字段置信度与原始依据 | 草稿 | 人工确认后提交 |

**③ 编排流程**
四层串行：输入层归一转写 → 编排层枚举步骤并由编排器决定调用顺序（不让模型一次性自由发挥）→ 执行层只对白名单内系统开放工具调用（写操作额外加一道确认）→ 复核层草稿态人工确认后提交业务系统。

**④ 关键配置**
原方案未涉及具体数值；工程约束为：模型侧与业务系统侧各做一次鉴权（不依赖单点校验）、不同部门知识库分开建索引、日志与业务数据分开留存。

**⑤ 失败与兜底**

- 任何一层出问题 → 单独定位，不因一次误判直接改动生产数据
- 写入异常 → 所有写入动作保留可回退路径，自动降级为「只出草稿、不落库」
- 灰度 → 先选重复度高、规则说得清、产出能量化的业务线小范围跑通再扩展

**⑥ 验收指标**

| 指标 | 目标值 |
| --- | --- |

### 5. 智慧餐饮云平台 + DeepSeek 智能分析：自然语言到指标到 SQL 的问数系统 【数据/餐饮·餐饮云平台·DeepSeek+MySQL+ClickHouse】

**① 场景与边界**

→ 结果回传 DeepSeek 解读 → 对话式回答 / 自动日报 / 异常归因
```

**④ 关键配置**

**⑤ 失败与兜底**

- 指标口径歧义 → 语义层同义词归一，禁止模型自创口径
- 非查询语句 → 安全校验拦截
- 幻觉数字 → 所有数字必须来自真实执行结果，模型不计算

**⑥ 验收指标**
原方案未涉及具体数值。

**机会点**：「语义层唯一口径 + 仅 SELECT 白名单 + LLM 只翻译不计算」是中小数据团队最稳妥的问数落地模式——第一步把现有数仓里 Top 20 高频指标写进语义层字典，再接 NL2SQL，一个月内可验证取数问答的可用性。

### 3. Anthropic always-on agents：事件收件箱 + 定时器 + 记忆的后台 Agent 【运营/后台任务·Anthropic 官方工程指南·五原语·参考架构】

**骨架来源**：Anthropic 官方工程指南《Building always-on agents》（William Hu，2026-11-13 发布），本文按 2026-11-16 发布的解析文章收录（在 48 小时窗口内）。**补全说明**：官方指南给出五原语架构与成本数字（②③与④的成本项齐全），⑥验收指标未给出，本文仅按官方成本数字补一条参照基线并标注，其余如实写「原方案未涉及」。

**① 场景与边界**

- 干什么：构建「感觉一直在运行、实际大部分时间在休眠」的后台 Agent——事件到达才唤醒、跑一小段（run）、保存记忆、再休眠；官方点名场景是追发票、告警分流、消息跟进。
- 输入：事件收件箱中的事件（用户回复、定时器到期、外部消息）。
- 输出：发件箱中的动作（回复用户、设置下次唤醒定时器、更新记忆）。
- 不干什么：不持续轮询烧 token；指南明确不覆盖多 Agent 协作等更复杂形态。

**② 工具清单**

| 组件 | 作用 | 输入 | 输出 |
| --- | --- | --- | --- |
| 事件收件箱（inbox） | 接收并暂存唤醒事件 | 外部消息/回复 | 待处理事件 |
| 定时器（timers） | run 内可设置未来唤醒 | 定时任务 | 未来事件 |
| 记忆（memory） | 跨会话保存上次学到的东西 | run 结果 | 下次 run 可用的记忆文件 |
| 权限（permissions） | 风险最集中的环节，控制自主动作边界 | 动作请求 | 允许/拒绝 |
| 发件箱（outbox） | 动作发出与降噪 | Agent 输出 | 送达用户的通知 |

**③ 编排流程**

```
休眠 → 事件到达（inbox）或定时器到期 → 唤起一次 run（加载系统提示+工具定义+记忆文件）
→ 完成任务 → 写回记忆 → 经 outbox 通知用户 → 回到休眠，无限循环
```

模型循环与普通 Agent 相同，新增架构全在模型外层：何时唤醒、哪些信息跨 run 保留、动作如何送达。

**④ 关键配置**

```
成本基线：Opus 5.5 在长程编码基准上每解决任务成本比 Opus 5 低 78%，典型负载低 40%（官方数据）
每次 run 固定开销 = 系统提示 + 工具定义 + 记忆文件重新加载（推理降价不消除此开销）
轮询守护服务（inbox/timer 监听）成本相对模型调用可忽略
步数上限/超时/温度：原方案未涉及具体数值
```

**⑤ 失败与兜底**

- 权限边界 → 指南将其列为「真正的风险所在」，需在唤醒间隙预先定义动作白名单
- 噪声问题 → outbox 层做降噪，避免每次 run 都打扰用户
- 死循环 → 靠定时器显式设定下一次唤醒，不靠持续轮询

**⑥ 验收指标**
原方案未涉及具体数值；可按「每任务成本、唤醒次数/任务、用户有效通知率」自建（# 推算：先以官方 40-78% 成本降幅为参照基线，对比同场景常驻轮询方案）。

**机会点**：五原语骨架 + 成本大降意味着「后台追单类」Agent（发票催收、告警分流）第一次做到休眠式低成本——给做运营自动化的团队第一步挑一个高价值低风险场景（如发票逾期跟进）照五原语搭最小版，两周可验证成本是否可接受。

来源：https://aiaffer.com/2026/11/anthropic-always-on-agents-sleep-events-2026 （解析；原始指南为 Anthropic 2026-11-13《Building always-on agents》，by William Hu）

### 4. 发票录入→支付就绪检查 stack：OCR + 制裁名单筛查的最小金融流水线 【金融/应付账款·MCP.Pub 社区·PaddleOCR+筛查 MCP·参考架构】

凭据=只读凭据                  # 原方案明确：acting 前必须验证
部署前核验筛查端点可用性        # 原方案明确
```

**⑤ 失败与兜底**

- OCR 文本质量差/置信度低 → 低于阈值转人工复核，不带病抽取

| 指标 | 目标值 |

- 输入：GitLab merge request 事件（diff 内容）。
- 输出：Markdown 评审报告。
- 不干什么：不接任何外部 API，不处理生产仓库（GitLab CE 沙箱测试）；只覆盖 macOS 环境指引（Linux/Windows 未涉及）。

**② 工具清单**

| 工具 | 作用 | 输入 | 输出 |
| --- | --- | --- | --- |
| Ollama（推理层） | 本地托管 Qwen 2.5 Coder 7B（代码分析特调） | diff/文件内容 | 评审分析 |
| LangGraph（编排层） | 有状态循环工作流、确定性控制流 | 评审任务 | 各步状态与结论 |
| GitLab CE（源控层，Docker） | 沙箱化 MR 事件源 | merge request | webhook 事件 |
| FastAPI webhook 接收器 | MR 打开时触发 Agent 工作流 | GitLab webhook | 工作流启动 |
| MCP（依赖项） | 预留标准工具接口 | — | 工具调用 |

依赖清单：langchain、langgraph、langchain-community、langchain-ollama、mcp、fastapi、uvicorn、python-dotenv、requests。

**③ 编排流程**

```
GitLab MR 打开 → webhook → FastAPI 接收 → LangGraph 工作流启动
→ 拉取 diff → 本地 Qwen 2.5 Coder 7B 分步分析 → 路由到对应检查节点
→ 汇总输出 Markdown 评审报告（不回写 GitLab，人工读取）
```

**④ 关键配置**

```
模型=Qwen 2.5 Coder 7B（Ollama 本地，Apple Silicon）
recursion_limit=40               # 推导：LangGraph 官方默认 25，按多步评审放宽（同款公开实现 RedLineSoft 采用 40）
max_turns=10                     # 推导：Anthropic Agent 指南建议步数上限取真实负载 p95 略上
temperature=0.0                  # 推导：评审一致性场景通用取值
Python>=3.10（Homebrew 3.12 建 venv，规避系统 Python 3.9 冲突）  # 原方案明确
API 费用=0                       # 原方案明确
```

**⑤ 失败与兜底**

- 长 diff 超出消费级硬件承载 → 教程自认 7B 模型处理大 diff 会吃力，需分块或换更大模型（原方案未给具体方案）
- 评审质量无基准 → 教程未发布实测基准数据，上线前应自建回归集（原方案未涉及）
- macOS 限定 → Linux/Windows 企业环境需自行适配（原方案未涉及）

**⑥ 验收指标**

| 指标 | 目标值 |
| --- | --- |
| 全 PR 评审耗时 | ≤60 秒 # 推算：参照同类 LangGraph 并行评审项目实测（并行子 Agent 7-12 秒/个、全 PR 约 27 秒，Nishad Anil 2026-03 公开数据） |
| 评审评论可采纳率 | ≥60% # 推算：按 CI 评审工具噪声容忍常识设定，原方案未涉及 |
| 外发数据量 | 0（代码不出内网）原方案明确 |

**机会点**：安全政策禁止源码出内网的企业是明确空位——给内网研发工具团队第一步在一台 Mac mini/工作站上跑通「GitLab webhook → Ollama 评审」最小链路，用 20 个历史 MR 回放验证评论可采纳率。

## 本篇机会点小结

**一、最值得动手的一条**：国内第 3 条「制造业报价利润预审 Agent」。作者把全套可复用素材（报价台账模板、带测试数据的多层 BOM、制度文本、全套提示词）都放出来了，痛点具体（手工测算一单超 30 分钟、低价亏本单事后才发现），边界干净（只读不写、人工终审）。给谁做：制造业财务顾问/数字化交付商。第一步：拿素材给一家装备制造企业在私有化 Dify 上部署，两周内用「拦下几笔低于 12% 红线的报价单」验证价值。启动成本万元级，验证周期最短。

**二、被验证的需求**：国内第 2 条（阿里 open-code-review 在内部服务约两年、数万名开发者，token 成本压到通用 Agent 的 1/9——评审类 Agent 有人长期付费使用）；国外第 1 条（Bitmovin 用约 2 年演进到生产、routine 工单免人工闭环——客服 Copilot 真实跑在生产渠道）；国内第 4 条（客服团队从 10 人压到 3 人——降本结果已有数字）；国外第 3 条（Opus 5.5 长程任务每任务成本降 78%——后台 Agent 的成本前提已被官方数据确认）。

**三、明显的空位**：国内第 1 条与国内第 5 条（问数/归因类方案）架构写得扎实但全部缺失量化验收指标——谁先把「取数准确率、归因可追溯率」做成行业口径，谁就握住了这类项目的验收话语权。国外第 5 条（本地 PR 评审）教程承认未发布任何基准数据——本地化评审栈的效果验证工具本身是个空位。国外第 2 条（HITL 草稿审批）模式清晰但未产品化，抽成通用包即可占住「写操作安全审批」这个细分。

**四、本篇结论**：本篇说明 Agent 落地正在从「模型怎么选」转向「确定性工程怎么包」——国内两条头部方案（阿里 OCR、报价预审）的共同点是硬约束前置、模型只做判断、人工握住终审；国外则在把后台休眠式 Agent 的成本问题打通。还留在原地的是：问数归因类方案依旧普遍没有量化验收指标，多数团队仍凭感觉交付。
