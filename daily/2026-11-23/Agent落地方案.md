# 第一部分：国内 / China

### 1. 订单资产异常调查与补发审批 Agent：把"查一下，没发就补上"拆成证据、授权、执行三段 【客服·个人工程师复盘·Function Calling+Agent Loop+HITL】（发布于 2026-11-22）

掘金工程师 J船长发布《Agent 开发·阶段总结（一）》，用"订单 1001 已支付但金币未到账"这一个客服场景，把工具调用、执行循环、架构选型、协作审批四篇串成一条完整参考流程。作者明确说明这是参考流程而非生产部署，但六段骨架完整、边界意识极强。

**① 场景与边界**
- 干什么：受理"虚拟资产（金币）未到账"类客服诉求，自动完成调查→补发条件判定→人工审批→幂等执行→结果核对。
- 输入：用户自然语言诉求（含订单号，或由模型请求补充）。
- 输出：调查结论、绑定参数快照的补发申请单、可信业务系统的执行结果回执。
- 不干什么：不做退款、不做跨订单批量处理；不把用户口述当事实（须核对可信业务数据）；"查到异常记录≠符合补发条件、获得批准≠执行成功、模型说完成≠业务完成"——三件事分别由证据、审批、执行结果证明。

**② 工具清单**
| 工具 | 作用 | 输入 | 输出 |
|---|---|---|---|
| `get_order_status` | 查订单支付状态 | `order_id` | 支付状态 |
| `get_grant_record` | 查资产发放记录与错误码 | `order_id` | 发放记录（如错误码 `GRANT_TIMEOUT`） |
| `get_ledger_result` | 按原操作标识查可信账务入账结果 | `operation_id`（如 `grant-1001`） | 实际入账与否 |
| `create_reissue_request` | 创建补发申请并保存参数快照 | 订单/用户/数量 | 申请单 `req-1001` |
| `execute_reissue` | 业务系统幂等写入 | 申请+幂等键 | 唯一性受控的执行结果 |

**③ 编排流程**
```
用户诉求 → 后端+模型（Function Calling 选工具填参数）
  → [Workflow 固定主干] 查支付状态
      ├─ 未支付 → 说明当前状态，结束
      └─ 已支付 → 查发放记录
            ├─ 有结果且成功 → 回复用户，结束
            ├─ 超时/不明 → 按操作标识查账务（防"超时≠未发放"）
            └─ 确认失败且符合补发条件 → 创建申请（保存快照）
                  → 人工审批（HITL，挂起等待事件）
                  → 恢复：比对快照+重校验业务状态
                  → 幂等执行（业务层唯一标识去重）
                  → 核对执行结果 → 回执用户
异常原因不明时：局部 ReAct（按日志线索查服务/配置）
```

**④ 关键配置**
```
原方案未涉及具体数值。文中要求 Runtime 必须设三类预算：
执行轮数上限、工具调用次数上限、成本预算——但未给出值
```

**⑤ 失败与兜底**
- 发放接口超时 → 不当作未发放，按 `operation_id` 查可信账务结果，结果不明不得补发。
- 重试导致重复写入 → 复用业务幂等键，防重落在业务写入路径（唯一标识+同事务去重），不靠模型记忆或内存标记。
- 审批等待数小时 → 保存任务进度挂起，审批事件到达再恢复；恢复后重校验订单状态与批准有效性。
- 审批后参数被改 → 执行前逐项比对批准快照（申请/操作/订单/用户/数量），范围变化强制重新审批。
- 并发双请求都过检查 → 由业务系统保证同一笔发放只生效一次。

**⑥ 验收指标**
原方案未涉及（教学复盘，未给量化验收口径）。

**机会点**：这套"证据-授权-幂等执行"骨架是目前国内公开内容里把资产类写操作边界讲得最清楚的一份，可直接做成面向中小电商/游戏公司的"虚拟资产补偿"方案模板；第一步找一个真实发放系统按 50 条历史工单做回归验证。

来源：https://juejin.cn/post/7710577867138302015

### 2. 美团 FlexEval/FlexBench 指令条件化评测：用一条自有指令现场生成 Agent 验收考卷 【数据评测·美团技术团队·EMNLP 2026 论文】（解读发布于 2026-11-21，原论文收于美团 11 月 18 日 EMNLP 2026 精选）

美团技术团队 EMNLP 2026 论文《One Instruction Is a Benchmark: End-to-End Instruction-Following Evaluation with FlexBench》提出：不给模型固定综合考卷，而是拿你自己的业务指令现场生成可验证评测。掘金 11 月 21 日的解读把它翻译成了可直接落地的验收流程。

**① 场景与边界**
- 干什么：针对一条多轮业务指令（如退款 SOP、客服话术流程）现场生成评测对话，用两个指标验收 Agent/模型在该工作流上的真实表现。
- 输入：一条写清楚的目标指令（谁发起、前置条件、何时必须停下来问人）。
- 输出：COVERAGE（覆盖率：工作流推进到第几步）+ ACHIEVEMENT（达成度：每步条件是否满足）两个正交分数。
- 不干什么：不回答"哪个模型最强"（实验结论恰恰是排名不稳）；不评估成本与延迟；不提供现成评测维度（维度质量取决于指令质量）。

**② 工具清单**
| 组件 | 作用 | 输入 | 输出 |
|---|---|---|---|
| 维度导出器 | 从指令导出可验证评估维度 | 目标指令 | 一组"能判断对错"的条件 |
| 对话语料生成器 | 按维度生成指令条件化多轮对话 | 维度+指令 | 多轮对话语料 |
| FlexEval | 打分 | 对话+维度 | COVERAGE、ACHIEVEMENT |

**③ 编排流程**
```
① 把真实指令写清（发起人/界面/前置条件/停机条件）
② 按指令导出可验证维度，分成"覆盖"与"达成"两列
   （判据：能否用"走到没走到"回答——能则进覆盖）
③ 生成指令条件化对话 → FlexEval 出双分数
④ 四象限处置：走完但对得少→查每步判定依据；
   走得短但对→查中断条件（最易误判为通过）；
   又短又错→查意图识别；又全又对→可用
```

**④ 关键配置**
```
实验规模：9 条多轮指令 × 9 个当代 LLM = 3,888 段对话
工程参数（temperature 等）：原方案未涉及
```

**⑤ 失败与兜底**
- 指令写得含糊 → 导出的维度即含糊，"分数再精确也是精确地错"——前置动作是把指令写到可导出维度的粒度。
- 左上象限（走得短但对）被误判通过 → 用覆盖率做硬门槛："至少推进到第几步"。
- 回归集只有达成判据 → 每次回归同时统计"流程走到了第几步"。

**⑥ 验收指标**
| 指标 | 目标值 |
|---|---|
| 工作流覆盖率 | ≥90%（# 推算：依据原文"至少推进到第几步作硬门槛"的主张，数值为推算值） |
| 步骤达成度 | ≥95%（# 推算：多步流程每步 95% 才能保证端到端可用，推算值） |

**机会点**：绝大多数团队的 Agent 回归集"只有达成没有覆盖"，把 FlexBench 的双指标做成 LangSmith/Langfuse 的评测插件或开源"指令→评测集"生成脚本，第一步用一张覆盖/达成判据表给现有回归集体检。

来源：https://juejin.cn/post/7710348910824308736

### 3. 浏览器自动化内容发布 Agent：固定 Profile+固定启动参数把登录态做成资产 【运营·个人工程师·Chrome CLI】（发布于 2026-11-22）

掘金工程师发布《让 Agent 自己把文章发到掘金：一次真实的踩坑记录》，给出一条"人只负责登录、Agent 负责发布"的三段式浏览器自动化方案，参数级细节完整。

**① 场景与边界**
- 干什么：把写好的文稿自动发布到掘金等内容平台——进编辑器、填充、上传图片、提交。
- 输入：Markdown 文稿+目标平台。
- 输出：发布成功链接，或失败现场（会话状态/报错）。
- 不干什么：不代填任何凭据——密码/扫码/验证码必须用户本人完成（凭据进上下文即泄漏，且代填等于对抗风控）；不做平台授权范围外的操作。

**② 工具清单**
| 工具 | 作用 | 输入 | 输出 |
|---|---|---|---|
| Chrome CLI（四参数固定） | 打开/接管浏览器 | `CHROME` 路径、`PROFILE` 目录、`SESSION` 名、`LAUNCH_ARGS` | 可控浏览器实例 |
| 固定 profile 目录 | 登录态落磁盘复用 | `$HOME/.agent-profiles/juejin` | 持久会话 |
| 页面操作脚本 | 编辑器填充/上传/提交 | 文稿内容 | 发布结果 |

**③ 编排流程**
```
① 打开可见窗口 → 用户本人扫码/验证码登录（唯一人工步）
② Agent 接管同一个已登录会话（固定 profile，登录态复用）
③ 页面操作：进编辑器 → 填充正文 → 上传配图 → 提交
```

**④ 关键配置**
```
CHROME="/c/Program Files/Google/Chrome/Application/chrome.exe"
PROFILE="$HOME/.agent-profiles/juejin"   # 固定目录，禁用临时目录
SESSION="juejin-publish"
LAUNCH_ARGS="--disable-background-networking,--disable-component-update,
--disable-client-side-phishing-detection,--disable-domain-reliability,
--disable-breakpad,--no-first-run,--no-default-browser-check,--disable-sync"
# 每次调用四个参数必须带全；缺 --profile 或 --executable-path
# 会重建会话致选择器全报 of null
超时/重试参数：原方案未涉及
```

**⑤ 失败与兜底**
- 漏启动参数 → Chrome 后台连组件更新服务弹"HTTP 地址存在安全风险"拦截框，表面是"浏览器打不开/空白页" → 用全量 `LAUNCH_ARGS` 禁后台网络请求。
- 会话被重建 → 页面回到 `about:blank`、选择器报 null → 用同一套四参数重开，登录态自动复用。
- 凭据泄漏风险 → 登录段永远人工完成，Agent 不碰凭据。

**⑥ 验收指标**
原方案未涉及。

**机会点**：固定 profile+固定参数这套"会话资产化"打法可以直接扩展成多平台一键分发工具（掘金/知乎/公众号），第一步把四参数模板和登录态管理封装成开源 CLI。

来源：https://juejin.cn/post/7710905800151154738

### 4. Dify 官方客服机器人骨架 → 售后工单自动分流与知识问答 【客服·Dify 官方（LangGenius）·低代码工作流·参考架构】

**B 类说明**：骨架来自 Dify 官方教程《使用知识库搭建智能客服机器人》（问题分类→直接回复/知识检索→LLM 生成的节点图），Dify 为中国团队（LangGenius）产品。本条在其骨架上补全了第④段检索参数与第⑥段验收指标，补全依据为 Dify 社区实测配置（CSDN 实测文）与百度智能云 Dify 实践文。

**① 场景与边界**
- 干什么：站内客服消息分流——无关问题直接引导、产品咨询走知识库 RAG 回答、售后诉求按分类路由给对应处理人。
- 输入：网页/嵌入式聊天窗口的用户消息。
- 输出：带知识库依据的回答，或工单路由动作+通知。
- 不干什么：不执行退款等写操作；知识库查不到的明确答"需人工跟进"，不让模型编。

**② 工具清单**
| 工具/节点 | 作用 | 输入 | 输出 |
|---|---|---|---|
| 问题分类节点（LLM） | 分四类：无关/产品相关/名词解释/社群（可扩为紧急故障/技术咨询/产品反馈/普通咨询） | 用户消息 | 分类标签 |
| 直接回复节点 | 无关问题引导至帮助文档 | 分类标签 | 固定话术 |
| 知识检索节点 | 混合检索 FAQ/产品文档库 | 用户消息 | 召回片段 |
| LLM 生成节点 | 基于检索内容作答 | 召回片段+问题 | 回答 |
| IF/ELSE+Webhook（补全） | 按分类路由工单、触发通知 | 分类+检索结果 | 分配/通知动作 |

**③ 编排流程**
```
开始 → 问题分类
  ├─ 无关问题 → 直接回复（引导看文档）
  ├─ 产品咨询 → 知识检索 → LLM 生成（只基于检索内容回答）
  ├─ 技术咨询/紧急故障 → IF/ELSE 路由给对应产品线/技术团队+通知
  └─ 拿不准 → 兜底规则一律转人工
```

**④ 关键配置**
```
retrieval_mode=hybrid        # 依据：CSDN 实测文建议混合检索
top_k=4                      # 依据：同上
score_threshold=0.5          # 依据：同上
segment_length=500           # 依据：同上（分段 500/重叠 50 召回更完整）
segment_overlap=50           # 依据：同上
temperature=0.3~0.5          # 推导：依据百度智能云 Dify 实践文客服场景建议
分类模型：选更强的 LLM        # 依据：官方教程明确要求
```

**⑤ 失败与兜底**
- 分类不准 → 提示词补正反例、明确边界词；仍不准则退化为关键词硬匹配。
- 检索不中 → LLM 节点提示词写死"查不到就说需要人工跟进"。
- 知识库过期 → 文档每周更新一次、改版后立即重建索引。
- 误分配 → 分支条件加兜底规则，拿不准一律转人工。

**⑥ 验收指标**
| 指标 | 目标值 |
|---|---|
| 分类准确率 | ≥90%（# 推算：工单四分类业务常识） |
| 回答可溯源率 | ≥95%（# 推算：RAG 客服常识） |
| 转人工率 | ≤20%（# 推算：知识库覆盖良好的前提） |
| 首次响应时间 | <5s（# 推算：单检索+单生成的常规延迟） |

**机会点**：Dify 模板可以让交付方半天内给中小客户搭出可用的工单分流；第一步拿客户 5 类历史工单做分类测试集，四类全命中再发布。

来源：https://docs.dify.ai/zh/learn/tutorials/customer-service-bot ；参数实测参考 https://blog.csdn.net/gitblog_00956/article/details/155019877

### 1. LangChain 知识工厂：干活 Agent 只上报知识缺口，curator Agent 夜间修复 【数据·报表生成·LangChain 团队·flag 工具+curator Agent】（Harrison Chase 发布于 2026-11-21）

LangChain CEO Harrison Chase 发布《How to build a knowledge factory》，公开了 LangChain 内部在 GTM 与内容工作室 Agent 背后运行的"知识工厂"完整机制：执行 Agent 发现知识缺口只能上报，修复交给独立的 curator Agent 夜间完成。文中以营收报表 Agent 为完整示例。

**① 场景与边界**
- 干什么：维护让 Agent 长期干对活的公司知识——技能（SOP/脚本）、领域知识（口径/政策/事实）、取数指引——并通过 flag→curator 闭环持续更新。
- 输入：执行任务（示例：基于 BigQuery 原始营收数+Salesforce 数据准备营收报告）+ flag 记录+ Agent trace。
- 输出：报表本身；flag 队列条目；当晚更新后的技能文件。
- 不干什么：执行 Agent 永不直接写知识库（自己维护自己的知识会充满矛盾）；分钟级变化的数据不进知识工厂（每次现取，只维护"慢半边"：流程、口径、数据在哪）。

**② 工具清单**
| 工具 | 作用 | 输入 | 输出 |
|---|---|---|---|
| flag 工具 | 干活 Agent 上报"找不到/发现错"+建议修正 | 缺口描述+可选建议 | flag 队列条目 |
| curator Agent | 定时后台读原始来源+trace+flag，修复知识 | flag+trace+Slack/Notion 等原始来源 | 更新后的技能/文档 |
| 知识存储 | 技能存 GitHub、口径存 wiki、取数指引存 LangSmith Context Hub（或 Neo4j 知识图） | — | 可被 review 的知识文件 |

**③ 编排流程**
```
任务执行：营收报表 Agent 发现列改名 → 现场自行算对（任务不中断）
  → 调 flag 工具上报缺口
会话后：财务负责人与 Agent 协作调整格式，要求所有文档加新表头
当晚：curator 读 flag + trace → 更新相关技能文件（含新表头规则）
次日：Agent 直接用修复后的知识干活
```

**④ 关键配置**
```
curator 调度：每日夜间运行一次（原文 nightly，固定后台节奏）
其余参数：原方案未涉及
```

**⑤ 失败与兜底**
- 让干活 Agent 自己维护知识 → 充满矛盾且无人 review → 拆成两个角色，curator 只对来源与 trace 负责。
- 隐性流程无法沉淀 → trace 就是原料：把 Agent 执行轨迹喂给 curator，"工作揭示缺什么，补上后让后续工作更好"。
- 知识散落 → 存放在能被 review 的地方（GitHub 文件/Context Hub），而非无人看管的副本。

**⑥ 验收指标**
原方案未涉及。

**机会点**：用 Claude Code/Codex 的团队普遍缺"知识不烂尾"的机制，可照此做一个开源知识工厂脚手架（flag 工具+定时 curator+GitHub 技能库）；第一步把内部文档库接成技能仓库，跑一轮夜间修复看 trace 能修出什么。

来源：LangChain 博客《How to build a knowledge factory》（2026-11-21）；报道见 https://automater.ai/news/langchain-knowledge-factory-curator-agent-flagged-knowledge 与 https://mindpattern.ai/s/2026-11-22-langchain-s-knowledge-factory-lets-working-agents-flag-missing-company-knowledge-but

### 2. DuckDuckGo 设计→研发交接：机器可读 design spec + 检查跑两遍 【研发·设计协作·DuckDuckGo 设计工程师 Karl Koch·AI harness+CI】（发布于 2026-11-22）

DuckDuckGo 设计工程师 Karl Koch 发布长文：工程团队刚引入共享 AI 编码 harness（接任务→计划→写码→在运行中的应用里自检→带证据开 PR），设计侧必须给出机器可读的交接工件，否则编码 Agent 会把缺失信息"悄悄填上"。文中给出了可执行的分阶段方案骨架。

**① 场景与边界**
- 干什么：在设计阶段与 AI 编码 harness 之间放一个 design spec 工件（选定方向+参考截图+文案+所用 tokens），并让"设计一致性检查"在 Agent 循环内与 CI 各跑一遍。
- 输入：Asana 任务、Figma variables（设计 tokens）、探索工作区的模拟屏幕与文案导出。
- 输出：design spec 文件、一致性检查分数、低于阈值时给设计师的介入标记。
- 不干什么：模拟屏幕不是像素级唯一真源（跨平台可能需要不同控件）；分数不代替人看——初期阈值只用来"把人拉进对话"；spec 不是完整产品描述。

**② 工具清单**
| 工具 | 作用 | 输入 | 输出 |
|---|---|---|---|
| Claude project | 研究→假设→范围化提案 | 调研材料 | 提案 |
| 自研探索工作区 | 读任务、跨五平台模拟屏幕、导出文案与变更日志 | 任务 | 模拟屏+文案导出 |
| Asana | 任务承载 | — | 任务描述 |
| Figma variables | 设计 tokens 唯一来源 | — | token 值 |
| 编码 harness | 按命名约定发现并运行检查（含设计检查） | spec+代码 | 检查结果/PR |
| CI | 独立复跑同一检查 | 检查器 | 分数+标记 |

**③ 编排流程**
```
设计阶段产出 design spec（方向+截图+文案+tokens）
  → 编码 Agent 在自身循环内跑设计检查，修明显问题
  → CI 再独立跑同一检查（结果不依赖 Agent 自报）
  → 分数低于约定阈值 → 标记设计师人工比对
  → 方向变更时 spec 必须同步更新（缺失项宁可可见，不许 Agent 填空）
```

**④ 关键配置**
```
原方案未涉及（阈值具体值、检查器实现均未定——作者明确初期
只用阈值触发人工介入，先学检查哪里有用再加深依赖）
```

**⑤ 失败与兜底**
- 低分误报 → 可能是参考文件过期或检查器错，初期一律人工比对"检查结果 vs 界面实际"。
- tokens 多来源冲突（Figma/手写 Markdown/工具 JSON 并存） → 先决定哪个值可信、如何到达检查器、谁对分歧负责，再接自动化。
- spec 过期仍被引用 → 方向变更必须连动更新 artifact；字段缺失要显式可见。

**⑥ 验收指标**
原方案未涉及。

**机会点**：多平台团队都面临"设计 tokens 分散在 Figma/Markdown/JSON 三处"的同款问题；做一个小工具把 Figma variables 映射成检查器可读 spec，第一步为某一个设计系统定义 spec schema 并接一次 CI 复跑。

来源：https://karlkoch.me/writing/connecting-the-tools-is-becoming-the-work

### 3. OpenAI Agents SDK 退款客服参考架构：triage 交接 + 输入护栏 + 幂等退款 【客服·退款处理·OpenAI Agents SDK 官方示例·参考架构】

**B 类说明**：骨架来自 OpenAI Agents SDK 官方文档与示例工程（triage→billing handoff、`input_guardrail`、退款工具安全指引）；第④段与第⑥段由本篇补全：`max_turns` 取 SDK Runner 默认值，验收指标按客服业务常识推算。

**① 场景与边界**
- 干什么：客服消息分流与退款受理——triage 判意图后交接给账单专员，专员查单、发起退款，后端逐层校验。
- 输入：用户消息+认证上下文（`customer_id`、幂等键由应用注入，模型不可见）。
- 输出：路由答复，或通过工具校验的退款受理结果。
- 不干什么：triage 只路由不答题（"route, do not answer"）；模型请求不等于执行——退款必须过工具层与支付服务校验；输出不得宣称与工具结果不符的"钱已到账"。

**② 工具清单**
| 工具 | 作用 | 输入 | 输出 |
|---|---|---|---|
| `get_order_status` | 查订单状态 | `order_id` | 状态 |
| `process_refund` | 发起退款（模型可见参数不含 `customer_id`/幂等键，由应用注入） | `order_id`,`reason` | 退款受理结果 |
| `get_account_info` | 查客户账户信息 | `customer_email` | 账户概况 |
| `handoffs` | triage→账单专员的控制权转移 | 对话控制权 | 交接（上下文保留） |
| `input_guardrail` | 输入前拦截越权/无关请求 | 用户输入 | 放行/熔断 |

**③ 编排流程**
```
用户消息 → input_guardrail 预检
  → triage（指示：route, do not answer）
  → handoff 账单专员（handoff_description 写清"处理发票、扣款、退款"）
  → 查单确认 → 请求退款
  → 工具层校验：认证客户/金额/时间窗/支付状态
  → 支付服务：授权校验+幂等键去重（重复操作返回既有结果）
  → 输出检查：工具说 pending 就不许答"已到账"
```

**④ 关键配置**
```
max_turns=10            # 推导：Agents SDK Runner 默认执行轮数上限
退款重试：不自动重试，幂等键由支付服务去重  # 依据：官方 agent security 指引
其余参数：原方案未涉及
```

**⑤ 失败与兜底**
- triage 不交棒自答 → 收窄 `handoff_description`、强化"route, do not answer"，用代表性请求评测路由。
- 护栏误拦无害请求 → 关键词匹配漏同义词/拼写变体，换成测试过的分类器，误报与漏报分开度量。
- 退款重复执行 → 网络超时重试可能重复调工具 → 幂等键+支付服务为权威，重复操作返回既有结果。
- Agent 互相踢皮球 → 明确每个 handoff 的边界、去掉不必要的反向交接、设 run 预算。

**⑥ 验收指标**
| 指标 | 目标值 |
|---|---|
| 路由准确率 | ≥95%（# 推算：三路由客服常识） |
| 重复退款次数 | =0（依据官方幂等设计目标） |
| 退款类人工复核率 | ≤10%（# 推算） |
| 单任务成本 | ≤$0.10（# 推算：官方区间 $0.05–0.50/任务的低端） |

**机会点**：官方把"幂等键不进模型上下文、工具层做最后防线"定成了范式，中小支付/电商团队可以直接抄；第一步把这套护栏做成独立中间件，接一个支付沙箱验证重复退款拦截。

来源：OpenAI Agents SDK 官方文档与示例；实践拆解见 https://datarekha.com/agentic-ai/openai-agents-sdk

### 4. LangGraph 官方客服教程：三专员路由 + 退款 NodeInterrupt 人工卡点 【客服·工单路由与退款·LangGraph 官方教程·参考架构】

**B 类说明**：骨架来自 LangGraph 官方教程《使用小型模型的客户支持聊天机器人》（官方 StateGraph 节点图与退款挂起代码）；第④段补全依据 LangGraph 默认配置，第⑥段为推算。

**① 场景与边界**
- 干什么：按问题类型把用户请求路由到计费/技术支持专员，退款类写操作必须经人工授权后才恢复执行。
- 输入：用户聊天消息。
- 输出：分类后的答复，或"挂起等待人工授权"的退款请求。
- 不干什么：授权前退款一律不执行（`refundAuthorized` 状态门控）；不做多轮工单全生命周期管理。

**② 工具清单**
| 节点 | 作用 | 输入 | 输出 |
|---|---|---|---|
| `initial_support` | 初始分类路由 | 用户消息 | 路由决定 |
| `billing_support` | 计费专员处理 | 共享状态 | 答复/动作 |
| `technical_support` | 技术专员处理 | 共享状态 | 答复/动作 |
| `handle_refund` | 退款处理，未授权即抛 `NodeInterrupt` 挂起 | 状态中 `refundAuthorized` | 退款执行 |
| `StateAnnotation` | 共享状态（消息+授权标志） | — | 全局状态 |

**③ 编排流程**
```
__start__ → initial_support
  ├─ 条件边 → billing_support（计费/退款咨询）
  ├─ 条件边 → technical_support（技术问题）
  └─ 条件边 → 直接回复
计费分支中识别退款 → handle_refund
  → refundAuthorized=False → throw NodeInterrupt("人工授权必需")
  → 人工检查状态、确认退款合理 → Command(resume=...) 恢复
  → "Refund processed!"
```

**④ 关键配置**
```
recursion_limit=25      # 推导：LangGraph 默认步数上限换算
路由模型：小型模型即可    # 依据：官方教程定位（小模型客服场景）
退款门控：refundAuthorized 状态位  # 依据：官方教程代码
超时/重试：原方案未涉及
```

**⑤ 失败与兜底**
- 退款未经授权 → `NodeInterrupt` 挂起整个图，保留状态等待人工检查后恢复，而非直接拒绝。
- 分类路由错误 → 条件边按状态回退 `initial_support` 重新路由。

**⑥ 验收指标**
| 指标 | 目标值 |
|---|---|
| 路由准确率 | ≥90%（# 推算：三类路由业务常识） |
| 退款人工授权率 | 100%（依据教程 NodeInterrupt 设计意图） |
| 挂起→恢复成功率 | ≥95%（# 推算：依赖状态完整性） |

**机会点**：这是最快能跑起来的客服 Agent 起步模板——官方教程自带路由+人工卡点；第一步把计费/技术两个专员换成自有业务工具，挂一个真实审批人即可内测。

来源：https://github.langchain.ac.cn/langgraphjs/tutorials/chatbots/customer_support_small_model/

## 本篇机会点小结

**一、最值得动手的一条**：本篇外1（LangChain 知识工厂）。所有跑 Agent 的团队都卡在"知识烂尾"上，而 flag 工具+夜间 curator 这套闭环门槛最低——不需要新模型、不需要新平台，一个定时脚本+一个 GitHub 技能仓库就能起步；第一步把内部文档接成技能库跑一轮夜间修复，2-3 个月即可用"缺口修复数/回归通过率"验证。国内对应首选是国4（Dify 工单分流），千元级成本、两周可给客户交付。

**二、被验证的需求**：国2 显示评测需求已成规模——美团以 9 指令×9 模型=3,888 段对话的实验规模发表 EMNLP 2026 论文，说明大厂在为"按自己指令验收 Agent"投入研发；外3 的幂等退款护栏来自 OpenAI 官方安全指引，属于已被官方文档固化的付费级工程需求。

**三、明显的空位**：其一，国1 与国3 两位工程师各自把"审批快照""登录态资产化"做得极细，但都停在个人复盘，没人做成可复用模板——资产补偿与内容分发的模板化交付是空位。其二，外1 的知识工厂只有 LangChain 自己在内部跑，尚无第三方脚手架；其三，外2 点名的"tokens 三处来源冲突"（Figma/Markdown/JSON）在所有多平台团队普遍存在，却还没有现成检查器。

**四、本篇结论**：Agent 方案正在从"怎么编排"走向"怎么约束"——国内外的重点都落在预算、幂等、人工卡点与知识维护这些兜底件上；而"哪个模型更强"式的叙事已经没有方案价值，留在原地的是验收指标：8 条里仍有 5 条的第⑥段是空白。
