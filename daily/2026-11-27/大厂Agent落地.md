## 第一部分：国内

### 1. 美团 Keeta 客服模型用 RSI 闭环自己纠错，31B 模型跑赢线上强模型 【美团·客服售后·单Agent】

美团技术团队 11 月 26 日披露 Keeta（美团海外外卖业务）客服模型实践：用一个自研 31B 中等模型替换线上闭源强模型承接客服流量，动机是成本与可控性——闭源模型按调用计费、版本升级节奏掌握在供应商手里。方案结构是单 Agent 承接多轮会话：模型负责理解与决策，Skill/SOP 规定业务规则（退款、赔付、转人工），工具负责查询订单与配送状态；人工介入点在「巡检找错—归因定责」环节，由人判断错没错、错在谁、按哪一版 SOP 算错，再把纯模型错误构造为修复样本。护栏设计很细：归因先把工具和 SOP 的问题剔出去，只让模型学自己的错；修复样本按事发时的 SOP 版本构造、训练混合多版本，防止规则漂移；模型权重自持、版本节奏自主。接的内部系统是订单与配送状态查询工具和 SOP 版本库。效果数字明确：五轮迭代后 31B 模型线上 Bad Case 率降到原强模型的一半以下，满意度小幅反超。复制门槛在于巡检归因管线依赖业务规则沉淀，换一条客服线要重做 SOP 与归因规则，但「按 SOP 版本构造修复样本」的方法可直接迁移[来源](https://tech.meituan.com/2026/11/26/Agent-RSI-practice-in-meituan.html)。

**机会点**：客服 Agent 的「归因定责+按 SOP 版本构造修复」是最难自建的环节，中小团队基本手工做。有客服 SOP 经验的服务商可以做巡检归因外包与评估集产品，第一步拿已上线客服 Agent 的客户一周 Bad Case 做一份归因报告，两周内就能验证付费意愿。

### 2. 阿里云 AgentCore 一站式上下文工程：记忆、知识库、只读连接器三件套 【阿里·多环节·工作流】

阿里云本周为 AgentCore 企业智能体平台新增上下文工程能力，围绕三类资源组织企业 Agent 的「业务上下文」：记忆（会话摘要、语义记忆、用户画像、技能记忆四类提取，支持跨会话复用偏好与经验）、知识库（全文+向量混合检索、重排序、答案引用资料来源防幻觉）、连接器（对接 MySQL、PostgreSQL、SLS，Zero ETL 架构数据留在原系统、任务执行时按需查询）。覆盖场景是运营助手查订单异常、运维助手查故障日志、内部知识问答等通用环节。护栏设计：记忆按用户、Agent、会话归属字段隔离，应用服务端结合身份认证与权限校验限定读写范围；连接器只读、按业务权限限定查询范围、回答中标注时间范围与统计条件供用户核对；开发者可查看记忆正文与提取历史，修正过期偏好。平台统一管理自研、开源 Harness 与商业 SaaS 多来源 Agent。效果数字未披露（文中「上海仓 12,847 单」为演示示例）。复制门槛低——平台化配置为主，但换场景的知识库治理与权限映射仍需人工[来源](http://mp.weixin.qq.com/s?__biz=MzcwOTMzMTQyMA==&mid=2247517525&idx=1&sn=604cf062bef927c858b7b7fa3b2c96e2&chksm=f4c427d0fc6476f8c1aa13fb71433ed75f0a470d40429ece49229520307e200860cf8522a83c#rd)。

**机会点**：企业把内部数据接进 Agent 时，真正的实施黑洞是数据口径梳理和查询权限范围界定，平台工具再全也要人来做。服务商可从「连接器接入+权限范围清单+数据口径确认」切入做实施服务，第一步为一个试点部门把 MySQL 订单库和钉钉文档接入并写出权限范围文档。

缺口：效果数据未披露。

### 3. 华为 MindAgent 套件用多租户权限解决一体机多部门共用难题 【华为·多环节·工作流】

华为 11 月 26 日发布企业级 Agent 使能套件 MindAgent，与 AI 一体机配合，瞄准单部门试点向多部门推广的规模化断点：大量业务、个人、客户数据集中到同一台设备后，权限隔离、行为审计、问题追溯成为落地卡点。方案结构是「Skill 补动作执行+连接器打通业务系统+领域专家经验沉淀+企业 RAG 调取内部资料」四件组合，典型场景是合同审阅——读合同原文、调企业内部制度、对接审批系统后产出可落地结论。护栏是其核心卖点：依托多租户和精细化权限能力实现多部门共用一台一体机时模型、知识库、工具、算力四层相互隔离，对访问、数据、工具调用全链路安全管控与操作留痕；另内置定时 AI 巡检，自动输出负载与性能诊断报告。效果数字未披露。复制门槛体现在生态设计：伙伴构建行业 Agent 时不必每次重搭环境、重配权限，可把项目沉淀为可复用产品[来源](https://finance.sina.com.cn/roll/2026-11-26/doc-inkaappc3635432.shtml)。

**机会点**：一体机+多租户权限是政企市场的标准入口，行业 ISV 可基于 MindAgent 的 Skill 与连接器体系沉淀行业 Agent 产品，第一步先做合同审阅、制度查询这两个高频政企场景的 Skill 包，借华为渠道验证交付周期。

缺口：客户落地效果数据未披露。

## 第二部分：国外

### 4. AWS 开源 Strands Decider v2：内部工单分流成本降 98% 【Amazon·内部IT·工作流】

AWS 11 月 23 日（美西时间）开源 Strands Decider v2 决策模型家族：5 个基于 Gemma 4 的模型（E2B 到 31B，Apache 2.0 协议），不做文本生成，单次前向传播对 2-255 个预设选项打分并输出校准概率，用于工单路由、工具选择、是否转人工等高频小判断，选项变更时零重训。生产数据来自 Amazon 内部最大工单系统：用 Decider v1 E4B 替换 Claude Sonnet 4.6 做标注与分流后，成本降低 98%、响应延迟降低 78%。人工介入点设计为低置信度场景升级到人工复核。配套发布的 Box CLI 为编码 Agent 提供沙箱：拦截文件访问、Shell 命令、网络出口与 MCP 调用并按外部策略放行，API 密钥与 AWS 凭据存于沙箱外、仅在外发请求通过策略检查时注入——这是权限收敛的工程范本。复制门槛：模型开源可直接部署，但决策选项体系与分流规则要按客户工单体系重建[来源](https://digintoai.com/en/articles/aws-open-sources-strands-decider-v2-5-gemma-4-decision-models-under-apache-2-0-a-32307208ef05)。

**机会点**：「前置分流小模型+旗舰大模型分层」已在大厂被验证是企业 Agent 降本的最快路径。服务商可做决策模型微调与分流评测服务，第一步拿客户工单历史数据做一份「通用大模型 vs Decider 类小模型」的成本与准确率基准对比，两周可见结果。

### 5. Anthropic 发布 Claude Ship：审批权写成策略文件，人守最后一道闸 【Anthropic·研发·多Agent】

Anthropic 11 月 23 日发布 Claude Ship 测试版，把 GitHub PR 的后半程交给三个分工明确的 Agent：Code Review 负责结合整个代码库上下文从多角度找问题并做对抗验证（Quick/Standard/Deep 三档深度）；PR Steward 负责修 CI 失败、合并冲突与评审意见，边界明确——只修不批不合并，每次推送留言说明改了什么、怎么撤销；Claude Approvals 按仓库里团队自己写的 .claude/approvals.yml 策略文件做批准式审查，类似一个更聪明的 CODEOWNERS。护栏设计值得逐条对照：批准只是 GitHub 上的一个检查项，最终合并仍由分支保护规则决定；修改审批策略的 PR 始终需要两个人批准，防止顺手放宽规则；官方建议先跑 observe 观察模式积累信任再设为必需检查；组织可设月度支出上限；零数据保留、HIPAA 配置、客户自管密钥的组织暂不可用。效果数字（Anthropic 自报）：其 Claude Code 团队 6 到 9 月合并 PR 数量翻倍以上、被回滚的 PR 占比下降超过 40%，九成以上代码由 Claude 编写。复制门槛：依赖 GitHub 分支保护体系，GitLab、Bitbucket 等平台暂无等价物[来源](https://xiaoan.cc/article/claude-ship-fa-bu-pr-ping-shen-xiu-bug-pi-he-bing-yi-ci-jiao-bdu)。

**机会点**：国内用自托管 GitLab、腾讯工蜂、码云的大企业没有等价的「审批策略文件+必需检查」层。服务商可针对这类平台做等价实现——策略文件解析器加 CI 检查项插件，第一步给一个研发管理规范的客户把 CODEOWNERS 升级成带条件的审批策略并跑观察模式。

### 6. Google Cloud 定调企业 Agent 安全接入：策略必须长在请求路径上 【Google·多环节·工作流】

Google Cloud 11 月 24 日发布《Deploying agents safely in your enterprise》，核心结论是：当 Agent 从读信息转向在邮件、文档、数据集和云基础设施上自主行动时，仅有合法 OAuth 令牌不够，策略检查、数据边界、人工确认必须出现在请求路径上，而不是事后审计。配套动作：Workspace MCP 服务器正式商用，为 Gmail、Drive、Docs、Sheets、Slides、Calendar、Chat、Tasks 八类应用提供专用入口，入口内建权限与 DLP 检查、敏感操作人工确认、拒绝非智能体 OAuth 客户端，并与提示注入筛查协同；Google Cloud Agent Gateway 在协议层校验 Agent Registry 中的智能体身份、执行 IAM 与默认拒绝的出站规则、用 Model Armor 筛查请求；Workspace CLI 面向本地 Agent 使用范围受限 OAuth；2027 年 2 月起强制使用托管接口。这套方案回答了「Agent 能查谁的邮件、谁能撤销」的企业级问题：每次调用可识别「哪个 Agent 在以谁的身份做事」，管理员可审计并立即撤销。效果数据未披露——这是治理规范而非生产案例。复制门槛：依赖 Google Workspace 生态，其他办公套件需自行实现等价网关[来源](https://cloud.google.com/blog/products/identity-security/deploying-agents-safely-in-your-enterprise)。

**机会点**：国内企业接 Agent 进办公与业务系统时，普遍用的是共享服务账号，审计记不到人。服务商可做「Agent 接入权限评估」服务——照 Google 这份清单给已上 MCP 的企业做一次调用链审计，产出身份传递改造与网关配置方案，两周内可交付第一份报告。

缺口：生产环境效果数据未披露。

【信息缺口】汇总：第 2 条（AgentCore 效果数据）、第 3 条（MindAgent 客户落地效果）、第 6 条（Google 方案生产效果）均未披露；第 1 条员工使用率与请求量未披露。

## 本篇机会点小结

**一、最值得动手的一条**：本篇第 1 条（美团 Keeta 归因闭环）暴露的「客服 Agent 巡检归因」是最值得动手的生意。给谁做：已上线客服 Agent 但效果不稳的电商、外卖、出行团队（国内这类团队今年已批量出现）；第一步做什么：拿客户一周线上 Bad Case 做一份归因报告，把错误拆成模型错、工具错、SOP 错三类并给出修复建议；多久验证：两周内客户要么为第二期付费、要么明确不要。选它而不是更热闹的审批策略层，是因为付费方已有 Agent 在跑、痛点已被自己的 Bad Case 率量化，不需要教育市场。

**二、被验证的需求**：第 4 条（AWS）内部工单替换通用大模型后成本降 98%、延迟降 78%，证明「分流降本」已进入生产账本；第 5 条（Anthropic）内部团队合并 PR 翻倍以上、回滚占比降 40%+，证明 AI 审查已嵌入真实交付流程且有人按 Token 付费；第 1 条（美团）31B 自研模型满意度反超闭源强模型，证明大厂愿意为「可控性」支付自研训练成本；第 3 条（华为）把多租户权限与审计做成套件核心卖点，说明政企客户已为此付费。

**三、明显的空位**：第 1 条的归因定责环节全靠人工规则判断，没有工具化产品，空在「归因自动化」；第 6 条 Google 已把「以谁的身份调用」讲成标准动作，而国内云平台（对比第 2 条 AgentCore 只有服务端权限限定）尚无对等的身份传递（On-Behalf-Of）与 Agent 网关产品，空在「国内版的 Agent 网关」；第 2 条平台能力先行但无效果数据，空在「生产验证案例」，先行实施服务商可以补位。

**四、本篇结论**：大厂 Agent 竞赛的重心正在从「模型多强」转向「权限怎么管、账怎么算」——放行权工程化与推理分层降本已是共识动作，但归因工具、国内 Agent 网关这类配套件还留在原地的手工时代。
